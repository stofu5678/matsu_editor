#   case-name | why

# The test (crates/ume/tests/sakura_oracle.rs) fails on a difference that is not listed here and on a

# Found when the oracle was widened (regular expressions and more command groups); not fixed yet.

# Found when the oracle was widened to saving in other codes, the conversion commands, Undo/Redo and caret moves (the cases save*, chgmod-eol-*, undo-*, caret-*, sel-*, box-edit-*); not fixed yet.
caret-move-cursor-past-line-end | MoveCursor(4, 40, 0) beyond the end of the line 'short': Sakura puts the caret one column past the end (InsText then gives `short <>`, with a space); UME clamps at the end of the line (`short<>`). Cause: CLayoutMgr::LogicToLayout (sakura_core/doc/layout/CLayoutMgr.cpp) answers a logical position beyond a line that has a line ending with `CalcLayoutWidth + 1` (the column of the line-ending mark), and Command_MOVECURSORLAYOUT (sakura_core/cmd/CViewCommander_Cursor.cpp) takes it as it is (GetAdjustCursorPos only fixes the row), so the caret rests where no key or click can put it and typing pads a space. A Sakura bug (ADR-0018 type A): kept on purpose
savecode-sjis-crlf-to-cp1200 | FileSaveAs with the code page number 1200 (UTF-16): CMacro::HandleCommand (sakura_core/macro/CMacro.cpp, F_FILESAVEAS) changes the code only when IsValidCodeOrCPType(1200) holds, which for a number >= CODE_CODEMAX asks IsValidCodePageEx -> ::IsValidCodePage (sakura_core/charset/charset.h); Sakura saved the Shift_JIS bytes unchanged, so the number was taken as not valid and ignored (inferred from the output; Windows' IsValidCodePage not run here). UME takes 1200 as UTF-16 LE (Encoding::from_sakura_code), which is what the macro writer meant; a Sakura quirk, kept on purpose (ADR-0018 type A, the user's decision on Sakura bugs)
savecode-sjis-crlf-to-cp51932 | a code that UME does not have (code page 51932 or 20932; UTF-32 was added on 2026-10-22): FileSaveAs gets it from the macro; Sakura saves in it (IsValidCodeOrCPType in sakura_core/charset/charset.h), UME writes no file and stays open with no dialog; a missing feature of UME (the encoding list has no MS-CP51932/20932), cause of the stall not investigated
saveloss-jp-to-cp1251 | Windows best-fit conversion: Sakura converts through WideCharToMultiByte without WC_NO_BEST_FIT_CHARS and without a used-default-char flag (`CCodePage::UniToCP` and `WideCharToMultiByte2`, sakura_core/charset/CCodePage.cpp lines 128 and 466; the flag is `WC_SEPCHARS`, line 24), so Windows maps full-width letters and digits to ASCII (`ＡＢＣ` to `ABC`, `１２３` to `123`; the oracle run) while U+3000 stays `?`; UME writes one `?` per character that the code page table does not have, and has no best-fit table (a new data file and its license are for the user to decide)
saveloss-jp-to-latin1 | Windows best-fit conversion: Sakura's `CLatin1::_UniToLatin1_char` (sakura_core/charset/CLatin1.h line 48) calls WideCharToMultiByte(1252, 0, ..., &blost) for what is outside U+0000..U+007F and U+00A0..U+00FF, without WC_NO_BEST_FIT_CHARS, so Windows maps full-width letters and digits to ASCII and U+3000 to a space (`ＡＢＣ　１２３` to `ABC 123`; the oracle run); UME writes `?` for each, and has no best-fit table (a new data file and its license are for the user to decide)

# タブにエディタ以外の機能を入れる検討（スーパーアプリ化）の調べ

[ADR-0024](../adr/0024-super-app.md) の下調べ。2026-10-24 にユーザーが「タブの中にエディタ以外の機能を組み込む、スーパーアプリ化が技術的にできるか検討。メニューアイコンやメニューの切り替えも検討」と頼んだ。

コードを読んで調べた。試作（`poc/super-app/`）は作っていない。読むだけで決まらないことは、末尾の「Windows と macOS で確かめること」にまとめた。

調べたコードは、このリポジトリの `main`（`5f81c9f2`）と、GPUI（`gpui-pre` 0.3.8、Apache-2.0）、gpui-component 0.7.1（Apache-2.0）。crates.io の版とライセンスは `crates.io` の API で 2026-10-24 に見た。Zed のエディタ・ターミナル・ワークスペースのクレート（GPL）は読んでいない。

## 1. 今のタブの作り

### 構造

- 1 つのウィンドウ（`Workspace`、`crates/matsu-ui/src/app.rs`）が `Tabs`（`tabs/mod.rs`）を持つ。タブ 1 つは `Tab { id, parked: Option<PaneSet> }`。アクティブなタブのペインは `Workspace::panes` に置き、ほかのタブは `parked` に預ける（[ADR-0015](../adr/0015-tabs-and-groups.md)）
- `PaneSet`（`panes/mod.rs`）は最大 4 つの `Entity<EditorView>` と、分割の位置を持つ。つまり**タブの中身は `PaneSet`、`PaneSet` の中身は `EditorView` と決まっている**。型に「エディタ以外」を入れる場所がない
- 1 つのプロセスに複数のウィンドウ（[ADR-0016](../adr/0016-single-instance.md)）。ウィンドウの一覧・次前のウィンドウ・タブの移動は `file_ops/windows.rs` が `Workspace` を数えて行う
- エディタ以外の物は、今は「ウィンドウに付くパネル」として入っている。検索・置換・Grep・DIFF・比較・設定のダイアログ（ウィンドウの中のパネル）、アウトラインとファイルツリー（右に付く `OutlinePane`）、ミニマップ、マクロのパネル。どれもタブではなく、アクティブな `EditorView` に紐づく
- サクラは Grep の結果、DIFF の印、ファイルツリーを、エディタの文書やパネルで見せる。MATSU も同じ作りにしてある。サクラの機能としては、エディタ以外のタブは要らない

### `EditorView` を前提にしている所

### 何が変わればよいか

最小の形は、タブの中身を列挙型にすること。

```rust
enum TabContent {
    Editor(PaneSet),
    Panel(Entity<AnyPanel>), // エディタ以外
}
```

エディタ以外の種類は 3 つ前後しか作らないので、`dyn` の特性（trait）より列挙型のほうが、`match` の漏れをコンパイラが見つけてくれる。[ADR-0013](../adr/0013-module-structure.md) の「全員が書き換える巨大な `match` を作らない」とは、コマンドの話で別。タブの種類は閉じた集合と見てよい。ただし、プラグイン（5 章）が種類を足せるようにするなら、特性にする。

「パネル」が満たす約束は、次の程度で足りる。

- 表題（タブのキャプション、ウィンドウのタイトル）
- 変更されているか、閉じてよいか（確認の質問を出せる）
- フォーカスを受ける（`FocusHandle`）
- メニューの種類（3 章）と、その種類の関数の使えるか・印
- ステータスバーの中身（なしでもよい）
- アクセシビリティの名前と役割

大きさの見積もり: タブの抽象化は PR 3〜5 本。`tabs/` と `file_ops/` を触るので、ほかの作業と衝突しやすい。ラウンドの間に挟むなら、他の担当の PR が少ない間に入れる。

## 2. 今のメニュー

| OS | メニューバー | 文書のメニュー・右クリック | アイコン |
|---|---|---|---|
| Windows・Linux | GPUI は OS のメニューを持たない（`gpui-pre-windows` と `gpui-pre-linux` の `set_menus` は一覧を覚えるだけ）。MATSU が自分で描く（`menu_bar.rs`、gpui-component の `AppMenuBar` を元にした） | GPUI のポップアップ（`PopupMenu`） | **出る**。`menu_icons.rs` が、サクラの `bMenuIcon`（既定は入）に従って、ツールバーの絵を列に描く |
| macOS | OS のメニュー（`cx.set_menus`、`gpui-pre-macos` の `create_menu_item` が `NSMenuItem` を作る） | GPUI のポップアップ。アイコンは出る | **出ない** |

- メニューの中身は 1 つ。`[MainMenu]`（`matsu-config` の `settings/main_menu.rs`）かサクラの既定から `app.rs` の `set_menus` が作り、`cx.set_menus` と、gpui-component の `GlobalState::set_app_menus` の 2 か所に入れる。Windows と Linux の `MenuBar` は後者を読む。だから今は**メニューがウィンドウごとに違うことはない**
- macOS では、ウィンドウがアクティブになったとき、関数を実行したあと、状態の写しが変わったときに、メニューを作り直す（`refresh_menu_states`、`defer_refresh_menu_states`）。GPUI は、OS のメニューが開く直前の呼び出しを MATSU に公開していない（内部で入力途中のキーの並びを捨てるだけ。`gpui-pre` の `init_app_menus`）。項目の可否は GPUI が `is_action_available` で聞くが、チェックの印と灰色は項目を作るときに決まる。だから MATSU は作り直す作りにしている。**実行時にメニューバーを入れ替える仕組みは、すでに動いている**

### macOS でアイコンが出ない理由と、出す方法

- GPUI の `MenuItem::Action` は `name`、`action`、`os_action`、`checked`、`disabled` だけで、画像を持たない。`create_menu_item`（`gpui-pre-macos` の `platform.rs`）も `setImage` を呼ばない
- 方法 A: GPUI を直す。`MenuItem` に画像の欄を足し、`create_menu_item` で `NSMenuItem::setImage` を呼ぶ。`gpui-pre` と `gpui-pre-macos` の 2 つのクレートに触る。ライセンスは Apache-2.0 なので、写しを持って `[patch.crates-io]` で差し替えるのは可能。改めたファイルには、Apache-2.0 §4(b) に従って改めたと書く。`gpui-pre` は毎週出る（Zed の snapshot）ので、版を上げるたびに当て直す手間が残る。Zed に PR を出す道もあるが、CLAUDE.md の「ほかの OSS への報告」のルール（ユーザーが確かめてから）に従う
- 方法 B: GPUI を直さない。`cx.set_menus` のあとで、`matsu-platform`（すでに `objc2-app-kit` の `NSMenu`・`NSMenuItem` を使っている）が `NSApp.mainMenu` を歩いて、`NSMenuItem::setImage` を呼ぶ。GPUI は項目に `tag` を振る（`create_menu_item`）が、その値は `menu_actions`（`set_menus` のたびに消えず、Dock のメニューとも共有する配列）の長さなので、作り直すたびに増える。0 から数えた添え字としては使えない。結び付けは、tag ではなく、メニューの木の形（上から何番目のメニューの何番目の項目か。MATSU が `set_menus` に渡した `Menu` と同じ並び）で行うgpui-component の `native_menu/macos.rs`（Apache-2.0）が同じ呼び出し（`NSImage::initWithData`、`setSize`、`setImage`）を使っているので、書き方の見本になる。足りないのは `objc2-app-kit` の `NSImage` の feature だけ。**読んだだけで、動かしてはいない**
- サクラのアイコンは色のついた 16×16 のビットマップなので、`setTemplate(true)`（文字色に染める）にはしない
- 起こりそうなこと（確かめていない）: メニューを作り直すたびに画像を付け直す必要がある。アイコンの列とチェックの印（`NSMenuItem` の state）の並びが、Windows の見た目と変わる。Retina 用の 2 倍の画像が要る

おすすめは方法 B（理由は ADR に書いた）。

## 3. メニューの切り替え

ユーザーの言い方は 2 通りに読めたので、両方を調べた。

### 読み方 1: タブの種類でメニューが変わる

エディタのタブではサクラのメニュー、データベースやターミナルのタブではその種類のメニュー。

- Windows・Linux: `MenuBar` が `GlobalState::app_menus`（アプリで 1 つ）を読む作りを、「ウィンドウのアクティブなタブの種類のメニュー」を読む作りに変える。`MenuGeneration` を見て作り直す仕組みがあるので、タブを切り替えたときにも通知すればよい。小さな変更
- macOS: タブを切り替えたときに、`defer_refresh_menu_states` と同じ道でメニューを作り直す。比べる写しに「種類」を足す。小さな変更。メニューバーの項目が変わるのは macOS では普通の動き（アプリごとにも、文書の種類ごとにも変わる）
- メニューの中身: エディタの種類は今のまま（`[MainMenu]` 以降）。ほかの種類は、メニューの定義が要る。`Entry` と `Item`（`menu.rs`）はサクラの関数コードで項目を作るので、エディタ以外の項目は、関数コードのない「名前付きのコマンド」を呼べるようにするか、サクラにない関数コードの範囲を決める必要がある（[ADR-0008](../adr/0008-commands-and-keybindings.md) のコマンドは名前で呼ぶので、そちらを使えば足りる）
- サクラの互換: エディタのタブのメニューは変えない。新しい種類のメニューは、サクラの設定には出てこない。`matsu.ini` に書かせるかは、ユーザーの判断
- 共通で出したいもの: 「ファイル > 新規・開く・閉じる」「ウィンドウ」「ヘルプ」は、どの種類でも要る。種類ごとのメニューは、共通の部分とそれぞれの部分に分けて作る

### 読み方 2: 利用者がメニューのセットを選ぶ

サクラのメニュー、簡単なメニュー、自分のメニューから選ぶ。

- すでにある土台: `[MainMenu]`（`custom_menu` と共通設定のメインメニューの画面。仕様 CU）で、メニューを自分で作れる。選ぶ仕組みは、「組み込みのセットを数個持ち、選んだ名前を 1 つの設定に覚える」だけで足りる
- 組み込みのセットは、サクラの既定（今あるもの）に加えて、「簡単なメニュー」（よく使う項目だけ）を作る。何を入れるかは決める必要がある
- 選んだ名前を覚える場所は `matsu.ini`。サクラにない設定なので、置き場所と形はユーザーの判断（ユーザーのデータの扱いに当たる）
- 読み方 1 と両立する。「セットを選ぶ」は エディタの種類のメニューの選択肢を増やす話で、「種類で変わる」は種類ごとのメニューの話

## 4. エディタ以外のタブの候補

難しさ: 小 = PR 1〜2 本、中 = 3〜6 本、大 = 7 本以上か外の技術が要る。ライセンスは crates.io の表示（2026-10-24）。依存を足すには、ユーザーの判断が要る（CLAUDE.md）。

| 候補 | 難しさ | 要るもの | ライセンス | 言いたいこと |
|---|---|---|---|---|
| Markdown / HTML のプレビュー | 小 | gpui-component の `TextView`（`text::markdown`、`text::html`、すでに依存している） | Apache-2.0 | 新しい依存が要らない。HTML は JavaScript を動かさない部分集合。文書の変更に追従させるのは `SharedDocument` の変更通知を見ればよい。エディタの横に並べる使い方もあるので、タブが適するかは使い方しだい |

| 設定をタブに | 中〜大 | 今のダイアログはウィンドウ内のパネル。タブにするには、閉じる・保存の流れを書き直す | — | 見た目の得はあるが、価値は小さい。サクラはダイアログ |
| Grep の結果 | — | — | — | 今は文書に書く（サクラと同じ）。タブにする理由がない |
| ファイルツリー | — | — | — | 今はアウトラインのパネル（サクラと同じ） |
| ターミナル | 大 | `alacritty_terminal`（端末の状態と構文解析。ユニックスの PTY と Windows の ConPTY を `tty/` に持つ。0.26.0、2026-04-06 の版）。描画は自分で書く | Apache-2.0（`vte` は Apache-2.0 OR MIT、`rustix-openpty` ほかは MIT 系。依存を足すときに `cargo deny` で確かめる） | 下に詳しく |

### ターミナル

- `alacritty_terminal` は、端末の状態（グリッド、エスケープシーケンスの解釈、選択、スクロールバック）と、子プロセスの起動（Unix は PTY、Windows は ConPTY）を持つ。見ていないのは描画と入力で、そこは自分で書く。ほかに `portable-pty`（MIT、0.9.0、2025-02）、`vt100`（MIT、0.18.1）がある。Zed のターミナルのクレートは GPL なので、読まない・写さない
- 自分で書くもの: セルの描画（`EditorElement` のように、見えている行だけを描く）、色（16 色・256 色・24 ビット）、カーソル、選択とコピー、スクロール、サイズ変更（PTY へ伝える）、キー入力を端末のバイト列にする（矢印・ファンクション・修飾キー、Kitty 方式などは後回し）、貼り付け（括弧付き貼り付け）、IME（`EditorView` に入力の実装がある）、マウスの報告、シェルの選び方（`$SHELL`、PowerShell、cmd）、環境変数
- 難しい点: 幅の広い文字・結合文字・絵文字のセル幅（MATSU は `unicode-width` を使っている）、描画の速さ（大量の出力）、Windows の ConPTY の癖、Windows ARM64 での確認
- 安全: 子プロセスはユーザーの権限で動く。MATSU の `exec`（外部コマンド実行）と同じ。ただし対話的に動くので、貼り付けやエスケープシーケンスの扱いに注意が要る（セキュリティはユーザーの判断）
- 見積もり: 最小（出力が読める、入力できる、リサイズ、色）で PR 5〜8 本。使えるものにするにはその倍

### Web ビュー

- `wry`（Tauri の部品）は OS の Web ビューを使う。Windows は WebView2、macOS は WKWebView、Linux は WebKitGTK
- wry 0.57.1 の README（crates.io の tarball）に「ウィンドウのハンドルから作るのは Linux では X11 だけ。Wayland では GTK のコンテナを使う」とある。GPUI は GTK ではないので、**Wayland のセッションでは子ウィンドウとして置けない**（読んだだけで試していない）。X11 では置ける可能性があるが、GPUI のウィンドウとの組み合わせは未確認。WSLg や今のデスクトップの多くは Wayland
- Linux の実装は `webkit2gtk` クレート（MIT）と GTK のクレート（gtk-rs、MIT）を使い、実行時に共有ライブラリの `libwebkit2gtk`（LGPL-2.1 系。私の知識で、今回は確かめていない）を読み込む。CLAUDE.md は GPL 系（LGPL を含む）の**依存**を使わないと決めている。`deny.toml` が見るのは Rust のクレートで、OS の共有ライブラリは見ない（glibc も LGPL）。ルールが共有ライブラリにも及ぶのかはユーザーの判断
- Web ビューは OS の部品で、GPUI の描画の上に重なる（ポップアップメニューやダイアログが下に隠れるはず。確かめていない）
- 配布物の大きさ: クレートは小さい（`wry` の tarball は約 218 KB）が、Windows は WebView2 のランタイム（Windows 11 は入っている）が要る
- 結論: 優先しない。Web が要る機能は、先に OS の既定ブラウザで開く（`open` 系。すでに `matsu-platform` の `shell` がある）で足りるかを見る

## 5. プラグインがタブの中身を出す

[ADR-0007](../adr/0007-macros-and-plugins.md) は、マクロ（1 回走って終わる）を JSON-RPC で動かす形を決め、**プラグイン（常駐してイベントを受ける）は別の形で後で決める**としている。タブの中身を出すのは、常駐するプラグインの仕事なので、その後になる。

| 形 | 内容 | 費用 | 注意 |
|---|---|---|---|
| a. 宣言した画面を MATSU が描く | プラグインが「文字・表・木・ボタン・入力欄」などの木を JSON で送り、MATSU が gpui-component の部品で描く。操作はイベントで返す | 中〜大。画面の記述の形（新しい公開の API）を決めて、互換を約束する必要がある | プラグインが固まっても MATSU は落ちない。アクセシビリティは MATSU の部品の分が使える。遅延はあるが表なら足りる |
| b. プラグインが Web ビューを出す | プラグインが HTML を渡す | 大 | 4 章の Web ビューの問題をそのまま受ける |
| c. プラグインが外のブラウザやアプリで出す | MATSU は URL を開くだけ | ほぼ 0 | MATSU のタブにならない |

先にタブの抽象化を作り、組み込みの種類を 2 つ作って、約束（表題・閉じる・メニュー・フォーカス）が安定してから a を考えるのがよい。今決めると、約束が固まる前に公開の API を作ることになる。

## 6. リスク

- 範囲と手入れ: エディタ（サクラの再現）が本業で、サクラの機能の穴を埋める作業（ラウンドごとに数 PR）はまだ続いている。タブの抽象化は `tabs/`・`file_ops/`・`app.rs` を触るので、その作業と衝突する。ターミナルは小さくならない（上の見積もり）
- 配布物の大きさ: 測っていない。`alacritty_terminal` は軽い（依存は `vte`、`regex-automata`、`polling` など）。Web ビューは OS のものを使うので、本体は大きくならない。測るのは実装するときにする
- アクセシビリティ: エディタの本文がまだ読み上げに出ていない（`a11y.rs`）。新しい中身はまず名前と役割だけを出し、本文は同じ時期に直す。ターミナルは本文が流れ続ける物で、扱いが特別に難しい
- サクラの互換: `[MainMenu]`、`[CustMenu]`、キー割り当て、ツールバーの設定は、エディタのタブについてサクラのまま読む。新しい種類のメニューや設定は、サクラにない節に書く。サクラの設定を読み込んだだけでは、エディタ以外の物は出てこない
- エディタの性能: 非エディタのタブは別のエンティティで、描画の経路を共有しない。`Workspace::render` の前半（タイトル、ステータス、ミニマップ）は種類で分けるが、エディタの描画（`EditorElement`）は変わらない。ターミナルの出力が速いときに UI スレッドを奪わないよう、読み取りは別スレッドにする
- 文書への範囲指定と全文の文字列を渡さないルール（CLAUDE.md、[ADR-0020](../adr/0020-huge-files.md)）は、文書を読むタブ（プレビュー）にも関わる。`TextView` の Markdown / HTML は文字列（`SharedString`）を受けるので、文書全体を渡すとこのルールに反する。プレビューは、上限を決めて超えたら無効にする、見えている範囲だけを渡す、などの決めが要る（未解決。プレビューの PR で決める）。文書を読まないタブ（ターミナルなど）には関係しない

## Windows と macOS で確かめること

試作を作らなかったので、確かめるのは実装の PR の中でよい。先に確かめるなら、次の小さな実験が 1 つずつで済む。

1. macOS: 起動したあと、`cx.set_menus` の直後に `NSApp.mainMenu` を歩いて、最初の項目の `NSMenuItem::setImage` に 16×16 の PNG を付ける（`matsu-platform` に `objc2-app-kit` の `NSImage` と `NSMenu` の feature を足す）。アイコンがメニューバーのメニューの中に出るか、メニューを作り直したあとも残るか、チェックの印と並ぶか
2. macOS: タブの切り替えに合わせて `set_menus` を呼び、メニューバーの項目の数や名前が変わっても、キーボードショートカットとフォーカスが壊れないか
3. Windows: 変わらない（メニューは MATSU が描く）。ウィンドウごとに違うメニューを `MenuBar` が読めるか。これは Linux でも確かめられる
4. Linux（X11 と Wayland）: wry の最小の例を GPUI のウィンドウの上に置けるか（X11 だけで動き、Wayland で失敗する、という読みを確かめる）

# 統合 GPU で MATSU が 400〜800 MB 使う理由の調査

調査日: 2026-11-16。GPUI（`gpui-pre-windows` 0.3.8）のソースと MATSU のコードを読んだ。Windows では動かしていない（測定は調整役の PC で行う）。ここに書く数のうち、「測った」と書いたものは調整役の測定で、「計算」は GPUI のソースの定義から出した値、「読んだ」はコードを読んだだけで動かしていないもの。推測は「推測」と書く。

結論を先に書く（2026-11-16 に、調整役の測定で確かめた）。

- 原因は、**2026-10-09 に調べて分かっていた Adreno の問題を、MATSU の本体に当てていなかったこと**。文字や画像を GPU のテクスチャ（アトラス）に書き込む（`UpdateSubresource`）たびに、Adreno X1-85 のドライバーがテクスチャを丸ごと複製して解放しない（1 回で 4 MiB）。回避策（`poc/gpui-textview/patches/gpui-pre-windows-atlas-upload.diff`）は試作にしかなく、`Cargo.toml` に `[patch]` はなかった（[ADR-0004](../adr/0004-ui-framework.md) は「本番では回避策を当てた GPUI を使う」と書いたが、実装していなかった）。
- 測定（調整役、ユーザーの PC: Windows 11 Arm64、Adreno X1-85、150 %、起動の 25 秒後）。回避策を当てると、回避策なしの 0.15.0 の 5 分の 1 ほどになった。

| ビルド | ワーキングセット | 専用 | GPU の使用中 | コミット済み |
|---|---|---|---|---|
| MATSU 0.15.0（回避策なし） | 397 MB | 411 MB | 359 MB | 407 MB |
| main c6637f58 に `gpui-pre-windows-atlas-upload.diff` を当てたもの | 73 MB | 80 MB | 27 MB | 75 MB |

- 書き込みの回数は数えていない（GPUI は数を教えない）。1 章の「説明されない約 100 MB」も、この測定で、アトラスへの書き込みによると確かめられた。
- ユーザーの判断（2026-11-16）: ADR-0004 のとおり、本番に回避策を当てる（別の PR が `third_party/` と `[patch.crates-io]` で行う）。ClearType は続ける。上流の報告はユーザーが出し済み（4 章・5 章）。

## 1. GPUI の DirectX 描画が確保するもの（読んだ・計算）

`gpui-pre-windows-0.3.8/src/directx_renderer.rs`、`directx_atlas.rs`。

### ウィンドウごとに 1 組（ウィンドウの大きさで決まる。大きさが変わると作り直す）

| 資源 | 大きさ | 1782x1180 での計算 |
|---|---|---|
| スワップチェーン | `BUFFER_COUNT`（3）枚 × 幅 × 高さ × 4 バイト（B8G8R8A8） | 24.1 MiB |
| パスの中間テクスチャ | 幅 × 高さ × 4 | 8.0 MiB |
| パスの MSAA テクスチャ | 幅 × 高さ × 4 × `PATH_MULTISAMPLE_COUNT`（4） | 32.1 MiB |
| 合計 | | **64.2 MiB**（1200x900 なら 33.0、2560x1440 なら 112.5） |

パスを 1 つも描かなくても、中間と MSAA のテクスチャは作る（`DirectXResources::new` → `create_resources`）。ドライバーが内部で足す分（並べ方の余白、タイル用の領域）はここに入っていない。

### 実体バッファ（種類ごとに 1 つ。`PipelineState::new`）

| 種類 | 1 つの大きさ | 作るときの個数 | 作るときのバイト数 |
|---|---|---|---|
| 影 | 112 B | 4 | 448 B |
| 四角 | 160 B | 64 | 10 KiB |
| 下線 | 64 B | 4 | 256 B |
| モノクロのスプライト（文字） | 112 B | 512 | 56 KiB |
| サブピクセルのスプライト（ClearType の文字） | 112 B | 512 | 56 KiB |
| カラーのスプライト（画像） | 96 B | 16 | 1.5 KiB |
| パスの頂点 | 32 B 相当 | 32 | 小さい |

（1 つの大きさは `size_of` で出した値で、`MATSU_GPU_DIAGNOSTICS` の出力と同じ。）

- バッファは `D3D11_USAGE_DYNAMIC`、毎フレーム `Map(WRITE_DISCARD)` で書く。足りなくなると `個数.next_power_of_two()` の大きさで作り直す（`update_buffer`、上限 `MAX_INSTANCE_BUFFER_SIZE` = 256 MiB）。**小さくする処理はない**。作り直すたびに `log::debug!("Updating {} buffer size from {} to {}")` が出る。
- 1 フレームの文字が 3000 個なら 4096 個ぶん = 0.4 MiB、10000 個で 1.8 MiB、40000 個で 7.0 MiB。つまり、画面に文字が何万個出ても、バッファは数 MiB。**これが数百 MB の原因にはならない**。ただし `DYNAMIC` + `WRITE_DISCARD` はドライバーが名前の付け替え（リネーム）で何枚か持つことがある（推測。確かめていない）。

### アトラス（文字・画像の置き場。種類ごとに 1 枚から。`DirectXAtlasTextures::push_texture`）

| 種類 | 形式 | 1 枚の最小（1024x1024） | 使うもの |
|---|---|---|---|
| モノクロ | R8（1 B/画素） | 1 MiB | グレースケールの文字、SVG |
| サブピクセル | R8G8B8A8（4 B/画素） | 4 MiB | ClearType の文字 |
| カラー | B8G8R8A8（4 B/画素） | 4 MiB | 画像（アイコン、背景画像、プレビューの画像） |

- 1 枚が埋まると、次の 1024x1024（置く物が大きいときはその大きさ。最大 16384）を作る。
- テクスチャが減るのは、その中の最後の 1 つを `PlatformAtlas::remove`（= `Window::drop_image`）で外したとき。**文字は外す手段がない**（ウィンドウを閉じるか、デバイスを失うまで残る）。画像は `drop_image` を呼ばない限り残る。
- 文字の登録のキーは、書体・字・文字の大きさ・拡大率・**横方向のサブピクセル位置 4 通り**（`SUBPIXEL_VARIANTS_X` = 4、縦は 1）・絵文字か・サブピクセル描画か・太らせ量。同じ字でも、大きさ、太字、サブピクセル位置が違えば別の登録になる。
- 書き込みは 1 つの登録ごとに `UpdateSubresource`（`DirectXAtlasTexture::upload`）。

### Adreno での問題（2026-10-09 に調べた。[結果](ui-framework-result.md)の「原因」）

試作（GPUI 0.3.8、同じ Adreno X1-85）で、使用中のアトラスへの `UpdateSubresource` 1 回ごとに、プロセスのメモリがちょうど 4.0 MiB 増え、解放されなかった。ステージング用の小さなテクスチャに書いて `CopySubresourceRegion` で写す回避策を当てると増えなくなり、起動直後が約 54 MB になった。グレースケールの文字（1 MiB のアトラス）は増え方が小さかった（NVIDIA と Mac では起きなかった）。Zed にも同じ機種の報告がある（zed-industries/zed#56349。調べた時点で「再現の確認待ち」）。

### 1782x1180 の計算と、最小のウィンドウの 170 MB

固定の分は 64.2 MiB。調整役の測定の最小ウィンドウ（GPU の使用中 170 MB）との差は、**約 100 MB が説明されていない**（最小のウィンドウの大きさは測定の記録にない。既定の大きさなら固定の分はもっと小さく、説明されない分はもっと大きい）。残りを説明できるのは、1 行の文字を出すための書き込み（ASCII の字 20〜30 種 × 4 MiB が 80〜120 MB）。**推測**であり、回数は数えていない。

## 2. MATSU が描くもの（読んだ。動かして数えてはいない）

描画の本体は `crates/matsu-ui/src/view/element.rs`（エディタ）、`terminal/element.rs`、`minimap/paint.rs`、`preview/view.rs`（gpui-component の `TextView`）、`bars/`、`menu_icons.rs`。

- **エディタの文字**: 表示している行（`p.rows`）だけを 1 行ずつ `shape_line` して `paint`。1 画面は 100 桁 × 50 行でも文字は多くて約 5000 個で、スプライトのバッファは 8192 個 × 112 B = 0.9 MiB。四角は行ごとの背景・選択・カーソル・括弧・行番号の背景で、数百から数千。画面の外の行は描かない。
- **隠れたタブ**: 表示しているタブの内容だけが描かれる（`tabs/content.rs`: 表示中の内容は `Workspace::content`、ほかは `Tabs` に持つだけ）。隠れたタブは描画のバッファを増やさない。
- **差分の印**（`view/diff_mark.rs`）: 印を 1 画素 1 個の四角で描く（`diff_mark::pixels`）。差分を出しているときだけ、行ごとに数十個の四角が増える。
- **ミニマップ**: 見えている行だけを小さな書体で描く（`minimap/paint.rs` の冒頭の説明どおり。巨大な文書でも行数に比例しない）。
- **ターミナル**: 表示している行の、背景が違う区間ごとの四角と、文字の区間ごとの文字。スクロールバック（既定 5000 行、[ADR-0028](../adr/0028-terminal-tab.md)）は CPU のメモリで、描くのは見えている行だけ。
- **プレビュー**: Markdown を gpui-component の `TextView` で描き、画像は `image_source` で文書の隣のファイルを `ImageSource::Resource` として読ませる。**画像は元の大きさのまま**デコードされ（4000x3000 なら CPU に 45.8 MiB）、アトラスに置かれる。1024 を超える画像はそれ専用のテクスチャになる（4000x3000 なら 45.8 MiB の GPU のテクスチャ）。プレビューのタブを閉じても `drop_image` は呼んでいない（MATSU で `drop_image` を呼ぶのは背景画像の `view/back_paint.rs` だけ）。GPUI の `img` が使う資源のキャッシュ（`use_asset`）も、アプリ全体で持ち続ける（読んだ。gpui-component 側の画像の扱いは読んでいない）。
- **アイコン**（`bars/icons.rs`、`bars/toolbar.rs`、`menu_icons.rs`）: ツールバーとメニューのアイコンは、1 つずつ PNG にして GPUI の `Image` として `img()` で描く。150 % なら整数倍（`pixel_factor`）して 32x32 か 48x48。1 つが小さい（4 KB 前後）のでアトラスの大きさへの効きは小さいが、**最初に描かれるたびに 1 回、カラーのアトラス（4 MiB）への書き込みが起きる**。メニューを初めて開くたびにアイコンが増える。ツールバーのボタンも同じ。
- **文字の登録の数**: エディタの書体と大きさ、行番号（太字が混ざる）、ルーラー、ステータスバー、タブ、メニュー（gpui-component の UI の書体）、ダイアログ、シェルのタブ（等幅の書体に替える）、プレビューの見出し（大きさ違い）。それぞれが別の登録になる。日本語の文書は字の種類が多く、各字が最大 4 通りのサブピクセル位置を持つ（桁の幅が整数でないとき。150 % の Windows では多くの場合そう、**推測**）。
- **Windows でサブピクセル描画になる条件**（読んだ）: ウィンドウの背景が不透明で（MATSU は不透明）、Windows の ClearType が有効なとき（`direct_write.rs` の `recommended_rendering_mode`）。測定した PC で ClearType が有効かは、確かめていない。

## 3. 診断（`MATSU_GPU_DIAGNOSTICS`）

`crates/matsu-ui/src/gpu_diagnostics.rs`。

- **変数は新しく作った**。`MATSU_FONT_DIAGNOSTICS` は、起動時に書体の長い報告を出す。こちらは短い行を繰り返し出すので、混ぜると見づらい。ロガーは `MATSU_FONT_DIAGNOSTICS` のものを共有する（`font_diagnostics::install_logger`）ので、GPUI の debug の記録（`Updating ... buffer size from A to B`）が標準エラーに出る。
- 起動時に 1 回: 資源ごとの 1 つの大きさと作るときの個数、バッファの伸び方の例、ウィンドウの大きさごとの固定の分（1 章の表）。
- 5 秒ごとに、変わったときだけ 1 行: 開いているウィンドウの数、文書の数、各ウィンドウの論理サイズ・拡大率・実画素数・固定のテクスチャの計算値。
- **GPUI が教えないもの**: 1 フレームの図形の数（`Scene` は `Window` の非公開の欄）と、アトラスの使用量（`PlatformAtlas` に問い合わせる手段がない）。バッファが伸びたときの記録だけが、1 フレームの大きさの目安になる。アトラスへの書き込みの回数は、診断では見えない（回避策あり・なしの測定で確かめた。冒頭）。
- 何もファイルに書かない。変数がなければ何も出さず、何も起きない。
- Windows で動かす PowerShell のジョブ: `C:\Users\yamab\ume-sandbox\jobs\gpu-diag-BUILD.ps1`（リポジトリには入れていない。調整役が測定に使う）。長い日本語の文書を開き、`PageDown`/`PageUp` でスクロールし、`ShellTab()` でシェルのタブを開く。別のプロセスで、4000x3000 の画像を含む Markdown を `PreviewTab()` で開く。各段階のワーキングセット、専用バイト、GPU のカウンター（`\GPU Process Memory(pid_N*)` の Local Usage、Shared Usage、Total Committed。GPU がなければ空）を `gpu-diag-<rev>-mem.txt` に、標準エラーを `gpu-diag-<rev>-err.txt` に保存する。マクロの書き方（`.mac`、`PageDown()`、`ShellTab()`、`PreviewTab()`、`Sleep()`）は、サクラのマクロの表と MATSU の機能の説明から書いただけで、**動かしていない**。

## 4. 直し方の案と、ユーザーの判断（2026-11-16）

1. **回避策を本体に当てる**: **決まった。別の PR で行う**（`third_party/` に手を入れた `gpui-pre-windows` の写しを置き、`[patch.crates-io]` で使う。GPUI の Windows 部分は Apache-2.0 なので、写しには改変の表示がいる。GPUI の版を上げるたびに当て直す）。上の測定で、効果は確かめた。
2. **ClearType をやめてグレースケールで描く**: **しない**（ユーザーの選択。ClearType は続ける）。
3. **プレビューの画像を小さくする**（表示する大きさに縮めてデコードし、タブを閉じたら `drop_image` で外す）: 回避策と無関係に効くが、回避策のあとの数字（73 MB）では急ぎではない。必要になったら別の PR で。
4. **ウィンドウの固定の分**（64 MiB）は GPUI の作りで、MATSU からは変えられない（上流の話）。

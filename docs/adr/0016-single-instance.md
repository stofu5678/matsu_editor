# ADR-0016: UME Editor を 1 つのプロセスで動かす

- 状態: 決定
- 日付: 2026-10-17（同じ日に、ユーザーが 1 つにまとめる案を選んだ）

## 背景

今の UME Editor は、`ume [path...]` を起動するたびに、別のプロセスとして動く。エクスプローラーなどからファイルを 2 つ別々に開くと、UME Editor が 2 つ動き、それぞれが自分のウィンドウだけを持つ。

サクラエディタは、ウィンドウごとのプロセスのほかに、コントロールプロセス（`sakura_core/_main/CControlProcess.cpp`、`CControlTray.cpp`）と共有メモリで、すべてのウィンドウをまとめている。2 回目以降の起動は、コントロールプロセスがあればそれを使い（`CProcessFactory::IsExistControlProcess`）、開こうとしたファイルがもう開かれていれば、そのウィンドウを前に出して終わる（`CNormalProcess.cpp` の `ActiveAlreadyOpenedWindow`）。プロファイル（`-PROF`）が違えば、別のまとまりになる。

UME Editor が別々のプロセスのままだと、次のことがサクラと違ってくる。

- ウィンドウの一覧、次・前のウィンドウ（PR #88）に、別に起動したウィンドウが出てこない
- 検索の履歴（PR #98）や最近使ったファイル（PR #95）が、ほかのプロセスとすぐには共有されない。設定ファイルを書くときにロックして合わせているが、動いている間の写しは別々になる
- タブバーを表示していても（ADR-0015）、外から開いたファイルがタブにならず、別のウィンドウになる
- もう開いているファイルを外から開くと、同じファイルのウィンドウがもう 1 つできる

## 決定

UME Editor は、1 つの設定ファイルにつき 1 つのプロセスで動く（2026-10-17 にユーザーが選んだ）。

- 2 回目以降の起動は、動いている UME Editor に、引数（開くファイルなど）と作業フォルダーを渡して、すぐに終わる。受け取った側は、サクラの規則で開く。もう開いているファイルはそのウィンドウを前に出し、タブバーを表示しているときはタブとして開く
- まとまりの単位は、使う設定ファイル（`ume.ini`）とする。サクラのプロファイルと同じく、設定ファイルが違えば別のプロセスになる。同じ OS のユーザーの間だけでつなぐ
- プロセスどうしの受け渡しは OS ごとに違うので、`ume-platform` に閉じ込める（ADR-0013）。macOS で Finder から開いたファイルは、OS から動いているアプリに届く。それも同じ入口で受ける
- 最後のウィンドウを閉じたら、プロセスは終わる（今と同じ）
- マクロを動かす `ume-script` は、今までどおり別のプロセスで動かす（ADR-0007）
- 2 つ目のプロセスとして動かしたいとき（試験や開発）のために、起動のオプションを 1 つ用意する

## 見送った案

- 別々のプロセスのまま、設定ファイルなどを通して合わせる案: 履歴は合わせられても、ウィンドウの一覧、次・前のウィンドウ、タブへの取り込みは、別のプロセスのウィンドウに届かない
- サクラと同じく、ウィンドウとは別にコントロールプロセスを常に動かしておく案: 仕組みが増えるわりに、1 つのプロセスにまとめる案より得るものがない

## 影響

- `crates/ume`（`main.rs`）は、起動したらまず動いている UME Editor を探し、あれば引数を渡して終わる。なければ自分が受け手になる。2 つが同時に起動したときも、受け手は 1 つに決まるようにする
- 受け手の入口は 1 つにして、コマンドラインから開くとき、外から渡されたとき、macOS の OS から届いたときで、同じ開き方をする
- 履歴のファイルのロック（PR #95、#98）は残す。設定ファイルが違うプロセスや、ほかの道具が同じファイルを書くこともあるため

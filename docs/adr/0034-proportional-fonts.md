# ADR-0034: 文字を、その文字の幅で置く（プロポーショナルフォントへの対応）

- 状態: 決定（2026-11-15 に、ユーザーが 4 つの質問をすべて推奨どおりと決めた）
- 日付: 2026-11-15（ユーザーが同日、サクラに倣うことを決め、先に ADR を書くよう頼んだ）
- 関連: [ADR-0013](0013-module-structure.md)（レイアウトは `matsu-layout`）、[ADR-0020](0020-huge-files.md)（巨大ファイルは範囲ごとに読む）、[ADR-0011](0011-printing.md)（印刷）、[ADR-0028](0028-terminal-tab.md)（シェルのタブ）、[ADR-0018](0018-decision-policy.md)（型 B）
- コードは変えない。この ADR は文書だけ

## 背景

2026-11-15 に、ユーザーが v0.14.0 を Windows で Noto Sans JP（プロポーショナルフォント）で試した。MATSU はどの文字も「半角のマス」の格子に置くので、幅の広い `m` は次の文字にぶつかり、狭い文字の横には隙間ができる。

- 今: 1 桁は半角の幅（`Metrics::cell_width`、`crates/matsu-ui/src/geometry.rs`）。レイアウトは桁で数え（`matsu-layout`、「桁」は半角 1・全角 2）、描画は `桁 × cell` に置く（`crates/matsu-ui/src/view/element.rs` の `place`）。
- サクラ: 文字ごとにフォントで幅を測って置く。
  - 幅: `CNativeW::GetHabaOfChar`（`sakura_core/mem/CNativeW.cpp`）が `CCharWidthCache::CalcPxWidthByFont` を呼び、`QueryPixelWidth`（`sakura_core/charset/charcode.cpp`）が `GetTextExtentPoint32W` で測る。固定幅のフォントで、半角より広い字形は半角の 2 倍に揃える（同ファイルの「半角より少しでも幅が広い場合は半角幅の2倍に揃える」）。結果は 65536 文字の表（`m_nCharPxWidthCache`）に覚える
  - 描画: 同じ幅を使う（`CTextMetrics::GenerateDxArray`、`sakura_core/view/CTextMetrics.cpp`。1 文字ずつの間隔の配列を作る）
  - レイアウトの X は画素（`CLayoutXInt`）。設定の「桁」は 1 桁の画素数 `m_nCharLayoutXPerKeta` を掛けて画素にする（折り返し `GetMaxLineLayout`・タブ `GetTabSpace`・タブの位置 `GetActualTabSpace`。`sakura_core/doc/layout/CLayoutMgr.h` の 115・153・188 行）。1 桁は「半角の幅 + 文字の間隔」（`CLayoutMgr.cpp` の `SetLayoutInfo`、150 行）。文字の間隔は 1 文字ごとに足す。足す量は「文字の間隔 × その文字の桁数（半角 1・全角 2。BMP の外は 2）」で、桁数は幅が半角以下なら 1、それより広ければ 2（`CLayoutMgr.h` の `GetLayoutXOfChar`、`CNativeW::GetKetaOfChar`、`CTextMetrics::GenerateDxArray`）。つまり全角の文字は間隔を 2 回足す。`W` の幅（`CLayoutMgr.cpp` の 156 行）は `m_tsvInfo.m_nMaxCharLayoutX` に入り、TSV・CSV モードのタブの長さにだけ使う（`CTsvModeInfo::GetActualTabLength`、`CLayoutMgr.h` の 178 行、`CMemoryIterator.h` の 97・106 行）。折り返しには使わない
  - 状態バーの桁は、キャレットの X を 1 桁の画素数で割った値（`sakura_core/view/CCaret.cpp` の 723・735 行）
- ユーザーが 2026-11-15 に、サクラに倣うことを決めた。それまでは、等幅のフォントを使うよう案内する。同日に別の PR で、エディタのフォントが等幅でないとき、シェルのタブは等幅のフォントで描く（端末の格子を保つため）ことも決めた。この ADR はそれを変えない
- 今の MATSU は、サクラと違い、幅をフォントでなく Unicode の規則で決める（`crates/matsu-layout/src/width.rs` の `WidthRule`。OS によらず同じ折り返しにするため。`crates/matsu-layout/src/lib.rs` に差の一覧がある）。プロポーショナルフォントへの対応は、この規則の外にも出ることになる

## 今、桁を数えている所と、変わること

調べ方: `columns_of`・`width.columns`・`WidthRule`・`cell_width`・`display_col`・`pos_at_col`・`goal_col` を `crates/` で検索し、主なファイルを読んだ。`matsu-commands` の個々のコマンドは、呼ぶ先（`Layout` トレイト）で分かる範囲に絞った。細部は段階 2 で確かめる。

「X」は、新しい単位（後述）で数えたレイアウトの横の位置。1 桁 = `per_column`（案 C では 64）。

| 場所 | 今、桁で何をしているか | 変わること |
|---|---|---|
| `matsu-layout` の `width.rs`・`config.rs`（`columns_of`、`widest_character`） | 文字の幅は Unicode の規則で 1 か 2。タブは `tab - x % tab` | 幅は「幅の表」から引く（X）。タブは `tab × per_column` の倍数の位置へ（サクラの `GetActualTabSpace`）。`widest_character` は、`Grid` では今の上限（タブ・TSV の区切り・全角・不正バイトの最大）のまま。`Table` では使わない（下の「巨大ファイル」） |
| `wrap.rs`・`map.rs`（折り返し、禁則、桁と位置の変換） | 桁の足し算。折り返しは `Wrap::Columns(n)` | 足し算の単位を X にする。折り返しの幅は `n × per_column`。型を `u32` の「桁」から X の別名の型にする（意味の取り違えを防ぐ） |
| `tsv.rs`（TSV・CSV の欄の幅） | 欄の最大の桁を求める | 欄の幅を X で求める。ファイル全体を 1 回走査する今の作りは同じ（文字ごとに表を引く） |

| `matsu-core` の `cursor.rs` | 矩形選択の隅と目標の桁を `usize` で持つ | 型は同じ（`usize`）。意味は「X」。コアは幅を知らないまま（幅を使うのは `matsu-layout` と UI） |
| `matsu-ui` の `layout_adapter.rs` | `char_columns`、`display_col` を `matsu-layout` につなぐ | X を返すようにする |
| `geometry.rs`・`hit.rs`・`view/mouse.rs`（当たり判定、`column_at`、フリーカーソル、矩形） | X 座標を `cell_width` で割って桁にする | X への変換にする。クリックした位置は、その行の文字の X を順に足して決める（文字ごとに幅が違うため） |

## 決めたいこと

### 1. フォントの幅を、UI からレイアウトへ渡す方法

依存の向きは UI → コアの一方向（`CLAUDE.md`）。`matsu-layout` は UI にも GPUI にも依存しない。そこで、レイアウトの側に「幅の表」を置き、UI は「1 文字の幅を測る関数」を渡す。

- `matsu-layout` に `Widths` を置く。2 つの形がある
  - 格子（`Grid`）: 今の `WidthRule`（Unicode の規則）で 1 か 2 桁を決め、`per_column`（文字の間隔を含む。半角 1 桁分、全角 2 桁分）を掛ける。フォントを見ない
  - 表（`Table`）: 文字の X の幅を表から引く。表は、サクラの `m_nCharPxWidthCache` と同じに、まだ測っていない文字を「0（未測定）」にしておき、引いたときに初めて測って入れる。BMP は 256 文字ずつのページに分け、使ったページだけ持つ（最大で 65536 × 2 バイト）。BMP の外の文字は小さな `HashMap`。幅は 1 以上（サクラの `std::max(1, size.cx)`）
- 測る関数 `Fn(char) -> u32`（`Send + Sync`）は UI が渡す。UI は、そのフォント（と代替のフォント）で、その 1 文字を shape して送り幅を測る。サクラも、文字ごとに使うフォントを切り替えて測る（`SelectHDC`）。制御文字は代わりの文字で測る（`QueryPixelWidth`）
- 表は `Arc` で共有する。`LayoutConfig` は `Clone` と `PartialEq` を持ち、`relayout_in` が `config == *self.layout.config()` で作り直すかを決めている。表の中身は比べず、「フォントの識別（世代番号）」で比べる
- 太字は、サクラと同じに、通常の字体の幅で置く（太字は同じ位置に太く描く）
- フォントが変わったとき（フォント、サイズ、文字の間隔、型の切り替え）: 新しい世代の表で `set_config` を呼び、`layout_for` で予算ごとに作り直す。今、折り返しやタブ幅を変えたときと同じ道。矩形選択は、桁が意味を失うので解除する（今の `relayout_in` と同じ）
- 巨大ファイル（ADR-0020）: 幅を測るのは、レイアウトが読む行の文字だけ（範囲ごと）。全文を走査して測ることはしない。表は文字の種類ごとに 1 回測るだけで、文書の大きさに比例しない。折り返しなしの行を走査せず 1 行と数える近道（`DocumentLayout` が `widest_character()` を上限として使う）は、その上限が本当の上限であるときだけ成り立つ。`Table` では、まだ測っていない字形がどれだけ広いか分からず、上限を証明できない（走査せずに飛ばした行の中の広い字形は、後から見つけられない）。そこで、`Table` ではこの近道を使わない。`Grid`（等幅）では今のまま使う（タブ・TSV の区切り・全角の上限が本当の上限）。費用: 比例フォントで折り返しなしの巨大ファイルを開くと、行ごとの行数を決めるために、すべての行の文字を表で引く走査が要る（今の等幅なら、バイト数だけの安い走査）。走査は予算ごとに進める（`layout_for`、先頭から表示できる）が、全体の行数・スクロールバーが確定するまでの時間は、ファイルの大きさに比例する。それが重すぎるときの手: 比例フォントでは、行のバイト数が `LONG_ROW_BYTES` を超える行だけを固定の長さで切る既存の作り（ADR-0020 の 9.10）に任せ、それ以外は 1 行ごとに数える。段階 4 で、巨大ファイルでの時間を測る。サクラの `W` の幅は折り返しに使わないので、この上限の根拠にしない
- 測る関数が使えるスレッド: 今、レイアウトは 1 フレームの予算（`LAYOUT_BUDGET`、`layout_adapter.rs`）の中で UI の側から進めている。GPUI で、`Window` を持たずに 1 文字を shape できるか、別のスレッドから呼べるかは、まだ確かめていない（GPUI のソースをこの下調べで読んでいない）。段階 0 の試しで確かめる。呼べないときは、必要な文字を UI のスレッドで先に測る（文字を引いたとき未測定ならレイアウトを中断して測る）形にする

### 2. 桁のまま残すもの（サクラと同じ）

設定の桁（折り返しの桁数、タブ幅、ルーラーの目盛り、状態バーの桁、横スクロールの「4 桁」）は、半角の桁で数え、X にするときに 1 桁の幅（`per_column`）を掛ける。上の表のとおり。「ウィンドウ幅で折り返す」の桁数（`window_columns` は `floor(幅 / cell)`）は、今のまま桁で数える。サクラが比例フォントで画素で折り返すかは確かめていないので、段階 4 で `sakura_core/view/` を読んで決める。

### 3. 等幅のフォントでは、今とまったく同じにする

- 等幅かどうかは、UI が ASCII の代表の文字（`i`、`l`、`.`、`M`、`W`、`0`）の送り幅を測り、同じ（誤差 0.01 画素以内）なら「等幅」とする。等幅なら `Grid` を使い、測る関数も表も使わない。幅は今の `WidthRule`（Unicode の規則）のままなので、折り返し・桁・描画の結果が今と同じになり、遅くもならない（表を引かない）。全角が半角のちょうど 2 倍でない等幅（Menlo と ヒラギノ角ゴシックの組み合わせ。`docs/sakura-gaps.md` の表にある）も、今のとおり格子に置く
- 検査: 案 A・C の途中の段階で、`Grid` の結果が「今の桁 × `per_column`」になることを、`matsu-layout` の既存のテストの期待値を X に直して確かめる。UI の段階では、等幅のフォントで描画が変わらないことを、既存のテストと画面の確認（`docs/e2e-screens.md`）で確かめる
- 限界: 等幅と比例の間でフォントを変えると、Unicode の規則とフォントの測定で幅が違う文字（等幅でもフォントが半角で描くギリシャ文字、など）の幅が変わる。等幅のときも、フォントで幅を決めるかは、フォントで測らないと決めた（決めたこと 3）

## 案

### 案 A: レイアウトの X を画素にする（サクラそのまま）

- レイアウトの X は整数の画素。`per_column` は 1 桁の画素数（半角の幅 + 文字の間隔）。幅の表は画素で持つ
- 長所: サクラと同じ。X が画素なので、描画の位置と同じ数をそのまま使える
- 費用・危険: 画面の倍率（DPI）、フォントのサイズ、ウィンドウを別のモニターへ動かしたときの倍率の変化で、必ず作り直す。MATSU の `cell` は小数（`f32`）で、整数の画素にすると、`1 桁 × 10240 桁` で端数が溜まり、今の描画と数画素ずれる（等幅で「今とまったく同じ」が守れない）。ずれを避けるには、等幅の格子だけ別の単位にすることになり、単位が 2 種類になる
- 失敗のしかた: 作り直しの途中で、キャレットや矩形の X が古い単位のまま残る（単位の混在）。型で別の名前にして防ぐ

### 案 B: コアは桁のまま、幅は UI だけで扱う

- `matsu-layout` と `matsu-commands` は今のまま（桁、Unicode の規則）。UI が、描画と当たり判定で、1 行の中の文字の画素の位置を自分で求める
- 長所: コアを変えない。最初の PR が小さく、コアの回帰が少ない
- 費用・危険: 折り返しが画素でなく桁なので、比例フォントでは行の見た目の幅がまちまちになり、ウィンドウからはみ出したり余ったりする。ルーラー、矩形選択（桁で持つ）、上下キーの目標の桁、横スクロールの最大が、画素と食い違う。「桁」と「画素の位置」の 2 つの座標を UI が常に行き来する。サクラとの差も大きい（サクラの矩形選択や折り返しは画素）
- 失敗のしかた: 行ごとに、桁の位置と画素の位置が食い違う。直しは、結局 A か C の作り直しになる

### 案 C: レイアウトの X を「半角の桁の 1/64」にする（推奨）

- 案 A の作りで、単位を画素でなく「半角の幅の 1/64」にする。文字の間隔の単位は `space_units = round(間隔の画素 × 64 / 半角の画素)`、`per_column = 64 + space_units`。幅の表に入れる値は、間隔を含めて `round(送り幅 / 半角の幅 × 64) + 桁数 × space_units` とする（桁数は、送り幅が半角以下なら 1、広ければ 2、BMP の外は 2。サクラが `GetKetaOfChar × 間隔` を文字ごとに足すのと同じ）。例: 半角の送り幅 8 画素・間隔 2 画素なら `space_units = 16`、`per_column = 80`、半角の字は `64 + 16 = 80`、全角の字は `128 + 32 = 160`。これで、表の幅・タブの位置・桁の設定が同じ `per_column` で合う。画素の位置は `X × (cell / per_column)`（`cell` は半角 + 間隔）
- 長所
  - 等幅は 64 の倍数で、2 のべきの割り算なので、`f32` で誤差が出ず、今と同じ位置になる（案 A の端数の問題がない）
  - 画面の倍率やフォントのサイズが変わっても、文字の間隔が 0 なら作り直さない（幅の比がほぼ変わらないため）。フォントの種類・文字の間隔・型が変わったときだけ作り直す
  - ミニマップが、自分のフォントの半角の幅だけで同じレイアウトを描ける
  - サクラとの差は単位だけ（サクラの画素を、半角に対する比に直したもの）。折り返しの桁・タブの位置・状態バーの桁は、サクラと同じ式で出る
- 費用・危険: 1 文字の幅の丸めが最大 1/128 桁。実際の送り幅（画素に丸まったもの）とは完全には一致しない。ただし描画も同じ X から 1 文字ずつ置くので、キャレット・選択・当たり判定は描画とずれない。ずれるのは、フォントの kerning や合字だけ（サクラの 1 文字ずつの置き方でも出ない）。文字の間隔が 0 でない型で、フォントのサイズを変えたときは作り直す
- 失敗のしかた: 表の測定がフォントの代替を取り違えると、その文字だけ幅が違う（描画は同じ表を使うので、重なりや隙間として見える。文字の位置は崩れない）

### 推奨

案 C。理由: 等幅で今とまったく同じにする条件（4 番目の要件）を、端数の問題なく満たせる。サクラの考え方（文字ごとに幅、X でレイアウト、設定は桁）をそのまま使う。画面の倍率やサイズの変化で作り直さないので、遅いファイルでも扱いやすい。案 B は最初の PR が小さいが、折り返しが画素と合わず、最終的に作り直しになる。案 A は C の単位が画素になっただけで、等幅の同一性を保つのが難しい。

## 段階（案 C の場合の PR）

どの段階も、等幅のフォントでは、画面もファイルも今と同じになること（上の「3」の検査）を条件にする。

0. 試し（小さい。コードの変更は捨てる試作か、診断用の出力だけ）: GPUI で 1 文字の送り幅を、`Window` なしで、別のスレッドから測れるか。Noto Sans JP などでの文字ごとの送り幅の表（`MATSU_FONT_DIAGNOSTICS` の出力に足す）。比例フォントで 1 文字ずつ置いたときの 1 フレームの時間（今の 1 行ずつ shape する描画との比較）。結果をこの ADR に追記する
1. `matsu-layout`: `Widths`（`Grid` だけ）と X の型を入れ、`columns_of`・`wrap`・`map`・`tsv`・`DocumentLayout` を X で計算する。`per_column` は 1。結果は変わらない（既存のテストがそのまま通る）。UI は `per_column = 1` のまま
2. `matsu-commands`・`matsu-core`: 桁の意味を X に読み替える（`display_col`・`pos_at_col`・矩形・フリーカーソル・空白の補い・マクロの関数）。`per_column` は 1 のまま。サクラの実装を読んで、空白を補う数え方を決める
3. `matsu-ui`: `per_column` を 64 にし、描画・当たり判定・ルーラー・横スクロール・IME・キャレット・ミニマップ・状態バーを X からの換算にする。等幅の見た目が変わらないことを確かめる（この段階が最も大きい。ファイルのまとまりで 2 つに分けてもよい）
4. 比例フォント: 測る関数、`Table`、世代番号、等幅の判定、1 文字ずつの描画、巨大ファイルで近道を使わないときの時間の測定。「ウィンドウ幅で折り返す」の扱い（サクラの実装を読む）。ここで初めて、比例フォントの見た目が変わる
5. 残り: 読み上げの位置、HTML のタブ展開、検索の強調の細部、ヘルプと README の「等幅のフォントを使ってください」の案内を外す
6. 印刷（別のシリーズ。決めたこと 2）

## 費用と、残ること

- 費用: 段階 1〜3 は、コードの量が大きい（表の「変わること」の全部）。ただし等幅の結果は変えないので、利用者には見えない。段階 4 で、比例フォントの 1 文字ずつの描画の費用が増える（GPUI が shape した行を覚えるので、同じ文字は安いと見込むが、段階 0 で測る）
- 比例フォントで、文字を 1 文字ずつ置くので、合字（fi など）と kerning は効かない（サクラも同じ）
- 残ること: 印刷、シェルのタブ（等幅のまま）、サクラが比例フォントで画素で折り返すかの確認（段階 4）

## 決めたこと

2026-11-15 に、ユーザーが 4 つとも推奨どおりと決めた。

1. 案 C（レイアウトの X を、半角の桁の 1/64 にする）で進める。段階 1 から順に PR を出す
2. 印刷は、このシリーズに入れない。画面が済んでから決める（段階 6）
3. 等幅のフォントは、今の幅（Unicode の規則）のままにする。等幅のフォントでは、フォントで幅を測らない
4. 等幅か比例かの判定を、設定で上書きする項目は、最初は足さない

## 段階 0 の結果

2026-11-16 に、段階 0 の 3 つの問いを調べた。読んだのは GPUI 0.3.8（`gpui-pre`、ワークスペースの版）で、以下の行番号はその版の `src/` の下。「確かめた」は動かして確かめたこと、「読んだだけ」はコードを読んだだけで動かしていないこと。この ADR の決めたことは変えていない。

### 1. `Window` なしで、別のスレッドから、1 文字の幅を測れるか

答え: 測れる。確かめたのは Linux（cosmic-text）だけ。Windows と macOS は読んだだけ。

- `Window` は要らない。幅を測る部品は `TextSystem`（`gpui-pre/src/text_system.rs` の 230 行）にあり、`App::text_system()`（`gpui-pre/src/app.rs` の 2220 行）が `&Arc<TextSystem>` を返す。`Window` が持つ `WindowTextSystem`（同ファイルの 603 行）は、その上に「行の覚え」（`LineLayoutCache`）を足しただけ。1 文字の幅は次の 2 つ
  - `TextSystem::advance(font_id, size, ch)`（433 行）: 1 つのフォントの字形の送り幅を引く。そのフォントに字形がなければ `Err`（「glyph not found」）。代わりのフォントには回らない
  - `TextSystem::layout_width(font_id, size, ch)`（446 行）: プラットフォームの `layout_line` で 1 文字を shape して、行の幅を返す。代わりのフォントにも回る（Windows は DirectWrite、macOS は CoreText、Linux は cosmic-text の代替）
- 別のスレッドから呼べる。`PlatformTextSystem` は `Send + Sync` を要求する（`gpui-pre/src/platform.rs` の 1441 行）。3 つの実装は、どれも中身を 1 つの `RwLock` で守っている（Linux `gpui-pre-wgpu/src/cosmic_text_system.rs` の 24 行、Windows `gpui-pre-windows/src/direct_write.rs` の 38〜41 行、macOS `gpui-pre-macos/src/text_system.rs` の 57 行）。`TextSystem` 自身も `RwLock` と `Mutex` だけで持つ。UI のスレッドにしか触れないという決まりはない
  - 確かめた（Linux）: `TextSystem` と `Arc<TextSystem>` が `Send + Sync` であること（コンパイル時の検査）。4 本のスレッドで 105 種類の文字を 20 回ずつ `layout_width` で測りながら、元のスレッドで 60 行を shape しても、幅は最初に測った値と同じだった（`poc/adr34-stage0`）
  - 読んだだけ: Windows の `DirectWriteTextSystem` と macOS の `MacTextSystem` が同じく `Send + Sync` であること（トレイトの条件なので、満たさなければビルドできない。CI が通っていれば満たしている）。スレッド越しの COM（DirectWrite）と CoreText の振る舞い（スレッドごとの制約がないか）は、動かして確かめていない
- 費用と注意
  - `layout_width` は、Linux・Windows・macOS のどれでも、プラットフォームの `layout_line` が書き込みのロックを取る（`cosmic_text_system.rs` の 273〜275 行、`direct_write.rs` の 289〜296 行、`text_system.rs`（macOS）の 206〜208 行）。測る間は、描画側の shape も待たされる。ただし 1 文字の測定は短い。105 種類の文字の最初の測定が、Linux で 0.3〜0.4 ミリ秒（下の 3）
  - `FontId` は先に決めておく（`TextSystem::resolve_font`（370 行）か `font_id`（329 行）。どちらも `Window` なし）
  - 結論: 測る関数 `Fn(char) -> u32` は、`Arc<TextSystem>`・`FontId`・サイズを持つ `Send + Sync` のクロージャにできる。**測る処理を UI のスレッドに限る必要はない**。段階 4 の「呼べないときは、必要な文字を UI のスレッドで先に測る」形は要らない見込み（Windows と macOS は段階 4 で動かして確かめる）
- 測り方の選択（段階 4 への影響）: `advance` は代わりのフォントに回らず、比例フォントに字形がない文字（かな、絵文字、`Noto Sans Mono` のかなや漢字）が `Err` になる。描画は代わりのフォントで描くので、幅は **`layout_width`（shape して測る）** で測る。`Err` の文字は 1 文字ずつ shape しないと幅が決まらない。結合文字（U+0301）は 0 になる（ADR の「幅は 1 以上」で受ける）

### 2. 文字ごとの送り幅の表

`MATSU_FONT_DIAGNOSTICS=1` の報告（`crates/matsu-ui/src/font_diagnostics.rs`）に、文字のグループごとの表を足した。描くフォント、入っていれば比例フォント（最大 3 つ。`Noto Sans JP`・`Noto Sans CJK JP`・`Yu Gothic UI` など）、等幅フォント 1 つについて、グループごとに 1 行、`文字 画素=単位`（単位は ADR の「半角の送り幅 `0` に対する比 × 64」）を出す。測り方は `layout_width`（上の 1）。

Linux（13 px）の結果（抜粋）:

| フォント | 半角 `0` | `i` | `m` | `W` | 空白 | かな・漢字・全角空白 | 半角カナ |
|---|---|---|---|---|---|---|---|
| Noto Sans CJK JP（比例） | 7.2 px = 64 | 32 | 107 | 101 | 26 | 13 px = 115 | 58 |
| Noto Sans Mono（等幅。かなは代わりのフォント） | 7.8 px = 64 | 64 | 64 | 64 | 64 | 13 px = 107 | 53 |
| Noto Sans Mono CJK JP（等幅） | 6.5 px = 64 | 64 | 64 | 64 | 64 | 13 px = 128 | 64 |

- 比例フォントの全角は、半角 `0` の 2 倍にならない（Noto Sans CJK JP は 1.8 倍、単位で 115）。1 文字ごとに表を引く ADR の作りが要る理由が、実測でも出ている。比例フォントでは、数字は同じ幅（64）で、`i` と `l` は半分（32 と 33）、`m` と `W` は 1.6 倍前後（107 と 101）
- 等幅フォントでも、かなが代わりのフォントになると 2 倍にならない（Noto Sans Mono は 107）。これは「等幅は Unicode の規則で 1 か 2 桁（決めたこと 3）」の根拠の 1 つで、等幅のときフォントで幅を測らないという決めたことを変える結果ではない
Windows（11 26100 Arm64、144 dpi、DirectWrite、ビルド 47df92d6、13 px）の結果（調整役が Windows サンドボックスで測った。報告の全文は `font-advances-47df92d6-default.txt`）:

| フォント | 半角 `0` | `i` | `m` | `W` | 空白 | ひらがな | カタカナ | 漢字・全角空白 | 半角カナ |
|---|---|---|---|---|---|---|---|---|---|
| BIZ UDGothic（既定の描くフォント。等幅） | 6.5 px = 64 | 64 | 64 | 64 | 64 | 128 | 128 | 128 | 64 |
| Noto Sans JP（比例） | 7.2 px = 64 | 32 | 107 | 101 | 26 | 115 | 115 | 115 | 58 |
| Yu Gothic UI（比例） | 7.0 px = 64 | 29 | 102 | 111 | 33 | 71〜97 | 82〜92 | 119 | 59 |
| Segoe UI（比例） | Yu Gothic UI と同じ表 | | | | | | | | |
| Consolas（等幅。日本語は代わりのフォント） | 7.1 px = 64 | 64 | 64 | 64 | 64 | 70〜95 | 81〜90 | 116 | 58 |

- Noto Sans JP は、Linux の Noto Sans CJK JP と同じ値（かなも漢字も 13 px 固定で 115）
- Yu Gothic UI は、**かなも比例**（あ 97、う 78、く 71、ア 92、コ 82 など。文字ごとに違う）。漢字と全角空白だけが 13 px（119）。したがって「全角は 1 種類の幅」という前提は、日本語フォントすべてには成り立たない。Segoe UI の表が Yu Gothic UI と同じなのは、日本語の字形を Yu Gothic UI の代わりのフォントから取るため。Consolas（等幅）も、日本語は代わりのフォントで、かなは比例になる
- BIZ UDGothic は、Linux の Noto Sans Mono CJK JP と同じく、半角 = 64、全角 = 128、半角カナ = 64 の格子に乗る
- この Windows の測定は UI のスレッドだけで動いた（ジョブは別のスレッドを試さない）。「別スレッドでの測定」は、Windows ではまだ読んだだけ（上の 1）

### 3. 1 文字ずつ shape する費用

`poc/adr34-stage0`（捨てる試作。ワークスペースにも CI にも入れていない）で、60 行 × 120 桁の日本語と ASCII の混ざった文字（4704 文字、105 種類、ASCII の断片と日本語の文を交互に並べる）を、`WindowTextSystem::shape_line` で shape する時間を測った。

- 環境: Linux（WSL2）aarch64、Qualcomm の 12 コア、リリースビルド、`bench_text_system()`（ウィンドウなしのプラットフォームのテキストシステム）、13 px、Noto Sans CJK JP（比例）と Noto Sans Mono（等幅）。15 回の中央値で、3 回動かして同じ傾向（下は 1 回の値）
- 測った時間: 1 画面分の `shape_line` の呼び出しの合計。測っていない: 文字の描画（`ShapedLine::paint`、字形のアトラス、GPU への送信）、`Window` が行う「行の覚え」のフレーム切り替え（`finish_frame` は非公開）。「次のフレーム」は、覚えを作り直さずに同じ覚えへもう一度引く形で近似した

| 形 | 最初のフレーム（覚えが空） | 次のフレーム（覚えにある） | 呼び出しの数 |
|---|---|---|---|
| 1 行ずつ（今の作りに近い） | 1.2 ミリ秒 | 0.02 ミリ秒 | 60 |
| 同じ種類（ASCII か、それ以外）の連なりごと | 0.4 ミリ秒 | 0.11 ミリ秒 | 338 |
| 1 文字ずつ（ADR の案） | 2.0 ミリ秒 | 1.3〜2.3 ミリ秒 | 4704 |

（Noto Sans CJK JP の値。Noto Sans Mono は、1 行ずつ 1.5 / 0.02、連なり 0.4〜0.5 / 0.11、1 文字 1.9 / 1.3〜1.5 ミリ秒。）

- 1 文字ずつでも、最初のフレームは 1 行ずつの 2 倍弱（2.0 対 1.2 ミリ秒）。文字の種類が 105 しかないので、覚え（`LineLayoutCache`。`text_system/line_layout.rs` の 668〜720 行）に当たる呼び出しが大半で、実際に shape するのは 105 回だけだから。ADR の「同じ文字は安いと見込む」は、この規模では合っていた
- 次のフレームは、1 文字ずつだと 1.3〜2.3 ミリ秒で、1 行ずつの 0.02 ミリ秒より 2 桁高い。覚えに当たっても、1 回ごとに文字列の確保と鍵の計算が要るため（1 回あたり 0.3〜0.5 マイクロ秒。この試作は呼ぶたびに `SharedString` を作るので、実際の作りでは減らせる）。60 fps の 1 フレーム（16.7 ミリ秒）に対して約 1 割で、それだけで間に合わなくなる量ではない
- 段階 4 に効くこと
  - 費用の大半は、shape でなく、1 文字ごとの呼び出しの回数（4704 回）にある。1 文字ずつ shape するときは、同じ文字の `ShapedLine` を（フォント・サイズ・色ごとに）自分でも覚えて、フレームの間で使い回すと、この呼び出しを減らせる
  - この測定に入っていない描画の費用（1 文字ごとの `paint`）が、段階 4 の本当の費用になる。段階 4 で、実際のウィンドウの 1 フレームの時間で測り直す
  - 巨大ファイルで近道を使わない場合の走査（`Table` の表を引く走査）の時間も、段階 4 で測る（ここでは測っていない）。表の最初の測定は、105 種類で 0.3〜0.4 ミリ秒（1 文字あたり約 3 マイクロ秒）

### この結果が段階 4 の計画に与える変更

- Windows の Yu Gothic UI は、かなが文字ごとに違う幅の比例になる（上の 2）。全角の幅を「半角の 2 倍」や「1 種類」と決めず、`Table` で文字ごとに引く作りが必要（等幅の `Grid` に回る判定は、ASCII の代表文字で行う ADR のとおりで、日本語の幅は判定に使わない）

- 測る関数は、UI のスレッドに限らず、`Arc<TextSystem>` を持つ `Send + Sync` のクロージャでよい（Linux で確かめた。Windows と macOS は、段階 4 で動かして確かめる）。レイアウトの予算の中で、`Table` の未測定の文字をその場で測れる
- 測るのは `advance` でなく `layout_width`（代わりのフォントを含めた幅）
- 測るときの書き込みのロックが、描画の shape と競合する。文字の種類は少なく（1 画面で約 100 種類）最初の測定だけなので問題は小さいが、Windows と macOS では、段階 4 で測る

## 段階 2 で決めたこと

2026-11-16 に、PR #474（段階 2）の「判断してほしいこと」にユーザーが答えた（すべて推奨どおり）。段階 2 は、`matsu-commands` のコマンドが持つ桁を X に読み替えた（`per_column` は 1 のまま）。

1. **行末より右に空白を補う数え方**: 空白の数は `ceil(補う幅 ÷ 半角の空白 1 つの幅)`。端数があれば 1 つ多く、挿入する文字は頼んだ位置より少し右から始まる。サクラの `CEditView::InsertData_CEditView`（`sakura_core/view/CEditView_Command_New.cpp` の 134〜155 行）が、`nSpWidth = CalcTextWidth3(L" ", 1)` ずつ `i` を進め、`i < 挿入位置 - 行の幅` の間、空白を足すのと同じ。`per_column = 1` では、補う桁の数と同じ個数で、今までと変わらない。実装は `CommandContext::spaces_to_fill`。空白の幅は `Layout::char_x(' ')` で、段階 4 で文字ごとの幅になっても、式は変わらない。改行のある行でサクラはループの終わりが改行の幅（画素 1 つずつ）のぶん短いが、MATSU は改行に画素の幅を持たせないので、改行のない行の数え方に揃える（違いが出るのは、端数がちょうど 1 X のときだけ）
2. **ソフトタブの空白の数**: `Command_INDENT` の `SSoftTabData::Len`（`sakura_core/cmd/CViewCommander_Edit_advanced.cpp` の 91 行）の式を X で数える: `(tab + w - (x + w) % tab) / dx`（`tab` はタブ幅の X、`dx` は 1 桁の X、`w = dx - 1`）。桁の少し先の `x` は、次の整数桁として数える。実装は `soft_tab_at`
3. **`matsu-core` の `Cursor`**: 目標の桁・フリーカーソルの桁・矩形の隅は `usize` のまま持つ。`matsu-layout` が `matsu-core` に依存するので、コアが X の型を名指しできない（循環する）ため。コアはこの数を保存して比べるだけで、桁に直したり計算したりしない。X との換算は `matsu-commands` の `context/units.rs` の 1 か所に置く
4. **マクロの関数**: サクラの設計（`sakura_core/macro/CMacro.cpp`）に従う。表示桁を渡す・返す関数（`GetSelectColumnFrom`・`GetSelectColumnTo`・`LineColumnToIndex`・`LineIndexToColumn`・`GetStrLayoutLength`・`MoveCursorLayout`）は X を使い、`GetDefaultCharLength`（2191 行、`GetLayoutXDefault()`）が 1 桁の X（`per_column`）を返す。`GetStrWidth`（2150〜2160 行）・`GetViewColumns`・タブ幅・折り返し桁は、サクラと同じく桁のまま。`per_column = 1` の今は、どれも以前と同じ数
5. **サクラとの違いの選択（段階 2 で決めた型 A・B）**:
   - 型 A: 矩形のスペースインデントで、サクラの「1 桁幅の矩形か」の判定 `1 == to.x - from.x`（`CViewCommander_Edit_advanced.cpp` の 172 行）は、X の 1 と比べているので、画素が単位だと 1 画素幅のときだけ真になる。意図は「1 桁幅」なので、`column_x` と比べる
   - 型 B: フリーカーソル・矩形の「左へ 1 桁」は `max(x - column_x, 行の文字の終わり)`。サクラ（`Command_LEFT`）は改行のある行で `max(x - dx, 終わり + dx)` で、`x` が桁の整数倍でないときだけ違う（今は整数倍しか出ない）

## 段階 4 の結果

2026-11-16 に、段階 4（比例フォント）を実装した。この ADR の決めたことは変えていない。ここに書くのは、実装で確かめた事実だけ。

- **表と等幅の判定**: `matsu-layout` の `Widths::Table`（`WidthTable`）。256 文字ずつのページ（使ったものだけ）、0 = 未測定、BMP の外は `HashMap`、幅は 1 以上、`Arc` で共有し、世代番号（作るたびに増える）で比べる。文字の間隔は「間隔 × 桁数（半角以下なら 1、広ければ 2、BMP の外は 2）」を表の値に足す。UI の `view/font_widths.rs` が、`i l . M W 0` の送り幅が 0.01 画素以内で等しければ `Grid`（測らない）、そうでなければ `layout_width` で測る表を作る。制御文字は、サクラの `QueryPixelWidth` と同じに、代わりの文字（NUL は空白、ほかは `･`）の幅と自分の幅の大きいほうで測る。フォント・太さ・斜体・サイズ・文字の間隔が変わると新しい表（新しい世代）になる。同じ組み合わせは、プロセスの中で表を使い回す（分割した窓枠が同じ世代を持つため）
- **描画**: 表のときは 1 文字（結合文字などを含むまとまり）ずつ、レイアウトの X に置く。shape した結果は、フォント・サイズごとに、色・太字・下線を鍵にして覚える（`ShapeCache`）。等幅の描画の道は変えていない
- **ウィンドウ幅で折り返す**: サクラは比例フォントでも画素でなく桁で折り返す。`CEditView::ViewColNumToWrapColNum`（`sakura_core/view/CEditView_Scroll.cpp`）が、ビューの画素数を 1 桁の画素数（`GetLayoutXDefault()`）で割って桁数にし、レイアウトはその桁数 × 1 桁の画素数で折り返す（`GetMaxLineLayout`）。MATSU の `window_columns` と同じ式なので、変えていない。同じ桁数でも、細い字（`i`）は多く、太い字（`m`）は少なく入る
- **巨大ファイル**: 表では、折り返さない行を走査せずに 1 行と数える近道は使わない（`widest_character` は `None`）。100 MB・約 104 万行・1 行平均 100 バイトの合成ファイル（`cargo test -p matsu-layout --release --lib -- --ignored --nocapture perf_report`、Linux aarch64 の 12 コア）で、全行のレイアウトが終わるまでの時間は、折り返さないとき 338 ミリ秒（格子）に対し 781 ミリ秒（表）、80 桁で折り返すとき 591 ミリ秒（格子）に対し 802 ミリ秒（表）。16 ミリ秒ずつ進めて 48〜49 回。測る関数は定数を返すものなので、実際のフォントの測定（約 100 種類の文字で 0.3〜0.4 ミリ秒）は含まない。先頭の 60 行は、どちらも 3〜64 マイクロ秒
- **段階 5 に残したこと**: ミニマップは、自分のフォントで文字列をまとめて描くので、比例フォントの文字の位置はレイアウトの X と細かくは合わない（置く位置の枠は X のまま）

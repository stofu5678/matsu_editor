# ADR-0020: 巨大ファイル（Phase 6）の設計

- 状態: 提案（ユーザーの決定待ち。決まるまで実装しない）
- 日付: 2026-10-21（ユーザーの依頼で下書きを書いた）
- 土台にする決定: [0005](0005-text-buffer-and-large-files.md)（ピースツリー 1 つ、元データは元の文字コードのバイト列、範囲ごとに読む）、[0012](0012-file-size-limit.md)（大きさの上限なし）、[0006](0006-regex-engine.md)（検索は行ごと、中断でき、別スレッド）、[0013](0013-module-structure.md)

## 背景

ロードマップの Phase 6 は「巨大なファイルをメモリに全部読まずに、範囲ごとに読んで速く開く」「改行位置をバックグラウンドで調べる」「ファイル全体を順に読みながら検索する」で、終わりの条件は「10GB のファイルを開いてすぐスクロールできる」。

ADR-0005 は方向だけを決めていた（編集の仕組みは分けない、元データの持ち方だけ差し替える、いくつかの制限）。この ADR は、実装の前に決めておくことと、確かめる手順を書く。数字（10GB、1 行 40 バイトなど）は、決めるための想定で、PoC（8 章）で測り直す。

### 今のコードの状況（2026-10-21 の main で読んだ）

差し替えの入口はもうある。

- `buffer::Source`（`crates/ume-core/src/buffer/storage.rs`）は `len()` と `read(start, end) -> io::Result<Cow<[u8]>>` だけを求める。今の実装は全体をメモリに持つ `MemorySource` と `file::FileBytes`。範囲を読む実装を足せば、ピースツリーは変えずに済む。
- ピースの位置は 64 ビット（`usize`）。行の索引 `LineIndex` は改行 1 つにつき 5 バイト（ADR-0012）。
- ファイルを開く `file::open_file_with` は、全体を `Vec<u8>` に読み（1MiB ずつ、進捗と中断あり）、文字コードを調べ、`Document::new` が全体を 1 回走査して索引を作る。表示は全部読み終わってから（ADR-0005 の「先頭が読めた時点で表示」は、まだ実装していない）。
- 状態を持つ文字コード（ISO-2022-JP、UTF-7）は、`Document::new` が全体を UTF-8 に変換して追加バッファに入れる。範囲ごとには読めない。
- 保存 `file::save` は一時ファイルに 1MiB ずつ書く。ただし `Document::chunks()` は 1 ピースを 1 回の `Source::read` で全部読むので、範囲を読む元データでは 10GB のピースが 1 つのバッファになる（直す必要がある）。
- `Document::line(i)`・`text_between` は、範囲を全部デコードして 1 つの `String` を返す。1 行が 1GB なら 1GB の文字列になる。
- レイアウト `ume_layout::DocumentLayout` は 1 行につき 4 バイト（行ごとの行数）を持つ。折り返しの行は表示する行だけ作る（小さいキャッシュ）。最初のレイアウトは分けて行う。
- 色分け `ume_coloring::ColorStates` は各行の先頭の状態を持ち、バックグラウンドで作る（遠い行の色が一度変わりうる）。
- 検索 `search::find` は行ごとに読み、`CancelToken` で中断でき、進捗を返す。`SearchJob` は別スレッドで動く。
- Grep は 1 ファイルを `open_file_with` で全部読んでから検索する。巨大ファイルを Grep に入れると、メモリに全部載る。
- 文字コードの判定は先頭 32KiB（`DETECT_SAMPLE_LEN`。サクラの `CFileLoad` と同じ）。
- ファイルのロック（`ume_platform::file_lock`）は、Windows は他のプログラムにも効く。macOS と Linux は助言ロックだけ。
- 依存: `memmap2` と `ropey` は GPUI 経由で `Cargo.lock` に入っている。ただし ume のクレートからは使っていない。

バックグラウンドで読んでいるもの: ファイルの読み込み（ただし表示は読み終わってから）、検索（`SearchJob`）、色の状態、レイアウトの最初の計算、Grep。全体が要るもの: 開くときの索引の作成、レイアウトの行数表、保存時の合計バイト数の計算（`total_len`）、アウトライン解析、「すべて選択してコピー」、すべて置換。

## 参考にした公開資料

実装は写さず、考え方だけ参考にする。

- VS Code の piece tree テキストバッファ（MIT）の解説「Text Buffer Reimplementation」（VS Code ブログ、2018）。ピースツリーの索引と、行の開始位置を持つ作り。
- ropey（MIT）、xi-editor の「Rope science」（Apache-2.0）。木のノードに集計値（長さ、改行数）を持つ作り。ume のピースツリーは同じ考え方で、すでに実装している。
- memmap2（MIT / Apache-2.0）の説明。`Mmap::map` が `unsafe` なのは、マップ中に他のプロセスがファイルを変えると未定義動作になるため、と書いてある。
- `man 2 mmap`（ファイルの終わりより先に触ると SIGBUS）と、Microsoft Learn の「Reading and Writing From a File View」（ビューの読み込みの I/O エラーは例外 `EXCEPTION_IN_PAGE_ERROR`）。
- Rust 標準ライブラリの `std::os::unix::fs::FileExt::read_at` と `std::os::windows::fs::FileExt::seek_read`（位置を指定した読み込み）。

GPL のコード（Zed のエディタのクレート、klogg など）は読んでいない。この章の OS の挙動の説明は、公開された文書による。この環境（WSL）では実機で確かめていない。確かめる項目は 8 章の PoC に入れた。

## 1. 元データの持ち方

### 案

- A: メモリマップ（`memmap2`）。ファイル全体を仮想メモリに写し、`Source::read` は `Cow::Borrowed` で返す。
- B: 位置を指定して読む（`read_at` / `seek_read`）。一定の大きさの塊（64KiB から 1MiB）を LRU のキャッシュに持つ。`Source::read` は `Cow::Owned`（複数の塊をまたぐとき）か、キャッシュからの複製を返す。
- C: 今のまま全部メモリに読む。範囲ごとに読まない。

### OS ごとの違い

| 項目 | メモリマップ | 位置指定の読み込み |
|---|---|---|
| ファイルが小さくなった（他のプログラムが切り詰めた） | Linux・macOS は、ファイルの終わりより先に触ると SIGBUS でプロセスが落ちる。Windows は `EXCEPTION_IN_PAGE_ERROR`（構造化例外）で、Rust のコードでは受けられない | 短い読み込みか `UnexpectedEof` のエラーになる。文書にエラーとして出せる |
| ネットワークドライブ | ページの読み込みが UI スレッドで止まる。接続が切れると上の例外 | 読み込みはバックグラウンドのスレッドに寄せられる。エラーは `io::Error` |
| Windows で開いている間の削除・置き換え | マップ中のファイルは切り詰められず、置き換えも拒否されることがある | 標準ライブラリの既定の共有（読み・書き・削除を許す）で開けば、置き換えられる（rename の意味論は PoC で確かめる） |
| 排他ロック（ADR-0010 の「排他制御」） | 同じ | 同じ。Windows で拒否されたら、ロックの許す範囲で読む |
| 速さ | キャッシュに乗れば最速。先読みは OS 任せ | コピーが入る。順に読む走査は `FILE_FLAG_SEQUENTIAL_SCAN` と `posix_fadvise(SEQUENTIAL)` で先読みさせられる |
| `unsafe` | 必要（memmap2 の `map`） | 不要 |

### 推奨

B（位置指定の読み込み + キャッシュ）。理由は 3 つ。

1. 他のプログラムがファイルを変える（ログの書き込み、同期ソフトの切り詰め）のは、巨大ファイルでは普通に起きる。メモリマップだと、これがプロセスの異常終了になる。位置指定の読み込みなら、エラーとして画面に出せる。
2. ネットワークドライブで UI が止まらない。
3. `unsafe` を使わずに済む。ワークスペースは `unsafe_code = "deny"`（`Cargo.toml`）で、ume-core に `unsafe` は無い。メモリマップ（memmap2 の `map` は `unsafe`）にすると、この決まりに例外が要る。

キャッシュの大きさは既定 64MiB（塊 256KiB × 256）を案にして、PoC で決める。ローカルのディスクで B が遅いと分かったら、「ローカルの通常ファイルだけ A」を後から足せる。`Source` の裏側の差し替えなので、API は変わらない。

### ファイルが外から変わったとき

- 開くときの `(長さ, 更新時刻)` を `Source` が覚える。読み込みが失敗したとき（短い読み込みなど）と、既存の `file_watch` が更新時刻の変化を見つけたときに、「ファイルが外から変更された」と表示する。
- 変わったことが分かった後は、保存を止める（元データが食い違っていて、壊れたファイルを書くため）。「名前を付けて保存」と「再読み込み」だけ許す。この止め方は、利用者のデータに関わるので 9 章の質問にする。
- 長さが増えただけ（追記）は、最初の長さまでを元データとして読み続ける。続きは再読み込みで読む。

## 2. 行の索引

### 問題

今の索引は改行 1 つあたり 5 バイト。10GB で 1 行 40 バイトなら 2.5 億行で約 1.25GB。1 行 10 バイトなら 10 億行で 5GB。ほとんど改行だけのファイルなら 100 億行で 50GB になる。これにレイアウト（4 バイト/行）と色の状態が加わる。上限なしで速く開く、には合わない。

### 案

- A: 今の索引（改行ごと）をそのまま使い、バックグラウンドで作る。メモリは行数に比例。
- B: ブロック索引。元データを約 64KiB ごとの塊に分け、塊ごとに「開始位置（64 ビット）」と「その塊の手前までの改行の数（64 ビット）」だけを持つ（16 バイト/塊。10GB で約 16 万塊、約 2.5MB）。行を探すときは、該当する塊を読んで中を走査する。塊の境界は CRLF を分けない位置にする。
- C: 一部の行だけ密に持つ（表示中の周りだけ）。

### 推奨

小さいファイルは今の密な索引（A）、範囲ごとに読むファイルは B。`LineIndex` の窓口（`agg(s, e)`、`nth_view`、`count_before`）を共通の形にして、2 つの実装を差し替える（ADR-0005 の「元データの持ち方だけを差し替える」と同じ考え方）。B の費用は、行 1 つを探すとき塊を 1 つ走査すること（64KiB の走査は memchr 相当で数十マイクロ秒の見込み。PoC で測る）。ピースの分割（編集）でも端の塊を 2 つ読む。読み込みの失敗は `BufferError::Io` で返す。

### 走査中に何が見えるか

- 走査は先頭から順に、ディスクの速さで進める。進んだ分（走査済みの先頭部分）の行番号は正確。
- 走査が終わるまで、**文書は読み取り専用**にする（推奨）。理由は、ピースツリーの集計値（改行の数）が不変の `Arc` ノードで、走査の進みに合わせて直せないため。もし編集を許すと、Undo の履歴にある古い版の集計値まで作り直す必要がある。10GB のディスク読み込みは、NVMe で数秒、HDD やネットワークで数十秒から数分。この間は読み取り専用で、状態表示に「改行位置を調べています 35%」を出す。走査中に編集したい要望が強いなら、後で「走査済みの先頭部分だけ編集可」を足す（9 章の質問）。
- 走査中の文書は、走査済みの部分だけを 1 ピースにした木を、数秒ごとに作り直して見せる。編集がないので、古い版を直す必要がない。
- 行番号は、走査済みの範囲は正確、その先は「約 N」（バイト位置の比率からの概算）と表示する。スクロールバーの長さは `全体の長さ × (走査済みの行数 / 走査済みのバイト数)` の概算。
- 行番号へのジャンプ: 走査済みならすぐ。未走査の行番号なら「走査が終わるまで待つ」か、概算位置に移る（案）。推奨は、概算位置に移ってステータスバーに「約」を出し、走査が終わった時点で行番号を確定する。表示位置は走査中は行番号でなくバイト位置で覚え、終わったら行番号に直す。
- ファイルの終わりへ移る（Ctrl+End）: 末尾の塊を読み、後ろから最後の改行を探して表示する。行番号は走査が終わるまで「約」。
- 走査はキャンセルでき（ファイルを閉じる、再読み込み）、読み込みエラーは表示に出す。

### 1 行がとても長いとき（1GB の 1 行）

- 索引（B）は改行がない塊を数えるだけなので、これ自体は問題ない。
- 問題は `Document::line(i)` が行全体をデコードすること。範囲ごとに読むモードでは、長さの上限（案: 1MiB のバイト数。設定にはしない）を超える行を「長い行」とし、表示・折り返し・色分けは行の途中の窓（上限の大きさの区切り）で行う。区切りの位置は 3 章の「文字の境界の目印」を使う。
- 長い行の中で編集することは許す（ピースツリーは、行の長さを知らなくても編集できる）。ただし、行の中の列の計算（タブの幅、全角）は、区切りの窓の中だけで行う。窓をまたぐ折り返しは、区切りで強制的に折り返す（簡易）。

## 3. 範囲の境界での文字コード

走査と読み込みは、塊の境界で文字を割らないようにしなければならない。ADR-0005 にあるとおり、SJIS・EUC-JP・UTF-8 の改行のバイトは文字の一部に現れない。ここを個別に確かめる。

| 文字コード | 改行の探し方 | 中から読み始めるとき | 扱い |
|---|---|---|---|
| UTF-8 | 0x0A、0x0D は 1 バイトの文字だけ | 続きのバイト（10xxxxxx）を最大 3 つ戻れば文字の先頭 | 簡単 |
| Shift_JIS（CP932） | 2 バイト文字の 2 バイト目は 0x40 以上で、0x0A、0x0D にならない | 2 バイト目が 0x40 から 0x7E のとき、ASCII と見分けられないので、途中からは文字の先頭が決まらない | 行の先頭（改行の直後）からだけ確実に読める |
| EUC-JP | 2 バイト目は 0xA1 以上。今のコーデックは 3 バイト文字（0x8F から）を扱わず、0x8F を不正なバイトとして次のバイトから読む（`encoding/euc.rs`）ので、3 バイト文字の分は考えなくてよい | 同じく、途中からは決まらない | 同じ |
| UTF-16 LE/BE | 2 バイト単位で見る。バイト単位で 0x0A を探すと、LE の 0x0A00 のような文字（上位バイトが 0x0A）を誤る | 偶数位置（BOM の後ろから数える）で始める。前の単位が上位サロゲートで、始める単位が下位サロゲートなら（正しいペアのときだけ）2 バイト戻る | 塊の大きさを偶数にし、CRLF（4 バイト）の途中で割らない。NEL・LS・PS を行の終わりにする設定（`ext_eol`）のときは、その文字も割らない。塊の終わりが文字の途中の不正に見えるときは、次の塊の先頭を含めて判定する（先読み） |
| ISO-2022-JP、UTF-7 | 状態を持つ | 途中から読むと、エスケープシーケンスの状態が分からない | 下の案 |
| その他（GBK、Big5 など 2 バイト文字のもの） | 2 バイト目が 0x40 以上のものは SJIS と同じ | 同じ | 同じ。ISO-8859 などの 1 バイト文字は境界の問題がない |

### 長い行の中の「文字の境界の目印」

SJIS・EUC-JP などは、行の途中から読むと文字の先頭が決まらない。行が短ければ行の先頭から読めばよいが、1GB の行では無理。そこで、走査が長い行（1MiB を超えるもの）を通るとき、約 1MiB ごとに「文字の先頭だと分かっている位置」を記録する（`Codec::char_len` で前の目印から文字を歩く。長い行だけなので費用は小さい）。目印は塊の索引に足す。UTF-8 と UTF-16 は目印なしでも決まる。

### 状態を持つ文字コード（ISO-2022-JP、UTF-7）

- 案 A: 今のまま、全体を UTF-8 に変換して追加バッファに入れる。メモリはファイルの大きさ程度。範囲ごとに読む閾値を超えたら、警告して許す。
- 案 B: 走査で、塊の先頭の状態（ISO-2022-JP なら 現在の文字集合 1 バイト）を記録し、`Codec` に「状態を指定してデコード」を足す。ISO-2022-JP は、行の終わり（CRLF）の前に ASCII か JIS ローマ字に戻すのが規格（RFC 1468）だが、戻さないファイルもあり、次の行は戻した先の文字集合から始まるので、状態は記録が確実。目印の位置は、エスケープシーケンスと文字の途中でない位置にそろえる。UTF-7 は base64 の途中の状態が要る。
- 推奨: 最初は A（閾値を超えたら「このファイルは全体を読み込みます」と確認を出す）。B は需要が分かってから別の PR で足す。巨大な ISO-2022-JP は珍しいため。UTF-7 は B をやらない。

### 判定と不正なバイト

- 文字コードの判定は先頭 32KiB で行う（サクラと同じ。`DETECT_SAMPLE_LEN`）。巨大ファイルで先頭だけを見て誤ることはありうるが、サクラと同じ挙動を保つ。利用者は文字コードを指定して開き直せる。先頭を ASCII だけで始まる巨大ファイルは、UTF-8 と判定される。
- 不正なバイトは、今と同じ（`INVALID_BYTE_BASE` の代用文字で表示し、編集していない部分は元のバイトのまま保存する）。範囲ごとに読んでも、塊の境界で割れたバイトを不正と見誤らないことが条件で、そのために境界は上の表の「文字の先頭」に合わせる。

## 4. 編集・Undo・保存

### 編集

ピースツリーはそのまま使う。元データのピースは `(開始, 終了)` の位置だけを持つので、10GB のファイルを 1 回編集しても、増えるのは数個のノードだけ。Undo は版の差し替えで O(1)（`undo.rs`）。範囲ごとに読むモードでも変わらない。追加バッファ（UTF-8）はメモリに持つ。貼り付けが何 GB もあるときの上限は、今と同じく無い（メモリが限度）。

### 保存（一時ファイルへ流して置き換える）

ADR-0005 のとおり、一時ファイルに書いて置き換える。変える点:

1. `Chunks`（`Document::chunks`）が元データのピースを 1 回で読まないようにする。元データの範囲は 1MiB 以下に分けて返す（今の `write_body` の `READ_CHUNK` と同じ大きさ）。`walk_events` の経路（別の文字コードや改行の変換）は、塊を 3 章の文字の境界に合わせて切る。
2. 保存前に、保存先のディスクの空き容量が（書き込む合計バイト数）以上あるか確かめ、足りなければ書き始めずに断る。一時ファイルが 10GB になるため、巨大ファイルでは起きやすい。
3. 進捗と中断は今の仕組みのまま。

### 読んでいるファイルに上書き保存するとき

編集していない部分は、まさに今保存で置き換えるファイルから読む。一時ファイルを作ってから置き換えるので、読みながら書くことはできる。問題は置き換えた後。

- 古いファイルは、置き換えると名前を失う。Linux・macOS は、開いているファイル記述子があれば、中身は読み続けられる（ディスクは解放されない）。Windows は、開いているハンドルが「削除を共有」していれば（標準ライブラリの既定）、置き換えられる見込み（Rust の `fs::rename` が POSIX 意味論を使う版に依存する。PoC で確かめる）。
- 保存後の Undo は、古いピースツリーが古い元データを指すので、古い元データを残しておく必要がある。

案:

- A: ピースの `Store` に「世代」を足す（`Original(世代)`）。保存後の文書は新しいファイルを 1 つのピースとして持ち、古い世代の `Source` は Undo の履歴が持つ間だけ残す。保存で作る新しいファイルの索引は、書きながら数える（改行の数を塊ごとに数えれば、再走査が要らない）。ディスクは、履歴が古い版を持つ間、古いファイルの分だけ余計に使う（Linux・macOS）。
- B: 保存したら Undo の履歴を捨てる。簡単だが、サクラは保存後も Undo できるので、サクラの挙動と違い、利用者のデータ（編集の履歴）に関わる。
- C: 同じファイルに直接書き込む（サクラの方式）。途中で失敗すると、元のファイルが壊れる。一時ファイル方式の ADR-0005 に反するので選ばない。

推奨は A。B は A が Windows で難しいと分かったときの退避策にする。

### 設計上の残りの課題（Codex によるレビューで分かったこと）

実装の PR で解くことを、先に書いておく。どれも推奨を変えるものではない。

- 読み込みの待ち: `Source::read` は同期で、レイアウトも `Document::line` を同期で呼ぶ。読み込みが遅いとき（ネットワーク）、描画が止まる。表示に必要な塊は、スクロールの前にバックグラウンドで先読みし、まだ読めていない行は「読み込み中」と表示する形にする（描画は待たない）。位置指定の読み込みは、短く読めることがあるので、読み切るまで繰り返す。
- ツリーの API: 索引が読み込みを伴うと、`LineIndex::agg`・`nth_view`、`Storages::piece`、`tree::split` がエラーを返せる形に変わる。ツリーの操作の全体にエラーを通す変更になり、3 番目の PR の大きな部分になる。
- 索引の費用: 短い行を 1 つずつ探すたびに塊を走査し直すと CPU を使う。直近に使った塊の改行の位置の表（デコード済みの位置）を、バイトのキャッシュとは別に持つ。
- 走査済みの先頭部分だけの木では、走査していない場所へのジャンプ、Ctrl+End、検索は、`Document` の API では表せない。これらは文書の API でなく、バイト位置を使う別の窓口（`Source` を直接読む）で行い、表示は「バイト位置で読んだ行」として出す。走査が終わったら、通常の文書に切り替える。
- 走査中に読み取り専用にする理由は、「集計値が分からない部分を持つ木の扱いを決めていない」ことで、ツリーの性質として不可能なのではない（古い版は元の木を持ち続けられる）。未知の集計値を持つ版と確定した版をどう混ぜるかの設計を省くための方針で、質問 3 で変えられる。
- 外から変わったときの検出: 長さが同じままの上書きは、読み込みのエラーにならず、キャッシュの古いバイトと新しいバイトが混ざる。更新時刻の確認（`file_watch`）に頼るため、完全には防げない。保存は止めるが、「名前を付けて保存」も混ざった内容を書きうるので、「変更が見つかったら編集と書き出しの両方で警告する」を足す。長さの増加が追記だけとは限らない。
- 長い行: 窓で表示しても、`pos_to_raw`・`line_len` などは行の範囲を読む。長い行の中の位置の計算、検索（正規表現は行全体の文字列を要る）、Grep は、長い行では窓ごとに行うか、制限（検索は長い行を飛ばして知らせる）を付ける。正規表現の中断は、行の途中では効かないため、長い行は窓に分けて探す。
- 保存の世代: 新しい世代は、自分の文字コード・索引・BOM を持つ。文字コードや改行を変えて保存したときは、保存後の文書を新しいファイルから読み直す（Undo の位置の意味が変わるので、その場合は履歴を捨てる）。Windows のロック（`DenyReadWrite`）では別のハンドルで読めない可能性があり、`RangedFile` の読み込みは、ロックを取ったハンドルを共有して使う。
- 保存の空き容量: `total_len` は元データのバイト数で、変換後の大きさではない。文字コードや改行を変えて保存するときの見積もりは、大きめ（元の大きさ + 追加バッファの大きさ + 余裕）にする。
- 検索の窓口: `SearchJob` は行ごとの進捗と最後の結果だけで、見つかった順に結果を出す窓口がない。バイト数の進捗と、途中の結果を出す窓口を足す。

## 5. 検索、すべて置換、Grep、ブックマーク、コピー

### 検索（次を検索、すべて検索、置換）

- ADR-0006 のとおり行ごと、別スレッド、中断できる。`search::find` と `SearchJob` はそのまま使えるが、行の取り出しが、塊の読み込みを伴うようになる。順に読むときは、同じ塊を何度も読まないよう、キャッシュと先読みの効果を測る（PoC）。
- 結果は見つかった順に出す（最初の 1 件がすぐ出る）。進捗は読んだバイト数の比率。
- 速さの上限は正規表現のエンジン（Onigmo の見込みで 100MB/s から 500MB/s）で、10GB なら 20 秒から 100 秒。案 1: 塊ごとに複数スレッドで探し、順序を保って結果を返す。案 2: 正規表現の特殊文字がなく、大文字小文字を区別する検索は、`memchr` / `memmem` で先に絞る。どちらも最初の PR には入れず、測ってから決める。
- 走査が終わる前の検索: 読み取り専用の間でも、検索は走査済みの範囲の先をバイト位置で読めるので、先頭から順に進められる。行番号は「約」。

### すべて置換

ADR-0005 のとおり、新しいファイルに書き出す。木の編集で何百万回の置換をすると、ピースが何百万にもなるため（ノード 1 つ数十バイト以上で GB になる）。

- 出力先の名前の決め方、元のファイルは変えないこと、置換の結果を開くかどうかは、利用者のデータに関わるので 9 章の質問にする。
- 置換は元データを順に読み、置換して、元と同じ文字コードで書く。進捗と中断あり。中断したら書きかけのファイルを消す。
- 範囲を選んだ置換と、選択範囲が小さい置換は今のとおり編集として行う。

### Grep

Grep は 1 ファイルを全部読むのをやめ、閾値を超えるファイルは塊を順に読んで行ごとに検索する（索引を作らない）。行番号は読みながら数える。ほかのコードに依存しないので、最初の PR にできる。

### ブックマーク（パターンで）

「該当行をマーク」は全行の検索なので、検索と同じく順に読み、中断できる。結果の行番号の表は 1 件 8 バイト。上限（案: 100 万件）を設けて、超えたら止めて知らせる。ブックマークは行番号で持つので、走査が終わるまでは使えない（走査中は「走査が終わってから」と知らせる）。

### すべて選択とコピー

- 選択は範囲（始点と終点の位置）で持つので、「すべて選択」自体は軽い。
- コピーに上限を設ける（ADR-0005）。案: 256MiB を超えたら断り、「ファイルに書き出す」ことを案内する。OS のクリップボードも大きな文字列に弱い。値は 9 章の質問。
- 切り取り・削除は選択範囲の削除なので、ピースツリーで軽い（削除した文字列を Undo 用にコピーしない作りは、今の `undo.rs` のとおり）。

## 6. レイアウト、色分け、アウトライン

| 折り返し（レイアウト） | 1 行につき 4 バイト（行ごとの行数）。折り返した行は表示する分だけ作る | A: 今のまま（2.5 億行で 1GB）。B: 行数の表は持たず、既定は 1 行 = 1 行として、表示した行の行数だけを疎な表に覚える。折り返す設定のときの全体の行数は概算。C: 範囲ごとに読むモードでは折り返さない | B。サクラの既定は折り返さない（折り返し桁数 10240）ので、既定の設定では A と同じ表示になる。折り返す設定では、スクロールバーの長さが概算になり、位置は（行, 行の中の何行目）で覚える |

## 7. 範囲ごとに読み始める閾値

### 案

- A: ファイルの大きさが閾値以上なら範囲ごとに読む。閾値は設定で変える（ADR-0005）。既定値の案: 256MiB。
- B: 既定値の案: 1GiB。
- C: すべてのファイルを範囲ごとに読む（全部同じ経路）。

### 推奨

A（既定 256MiB）。理由: 全部読む方式は、描画のたびの読み込みがなく単純で速い。256MiB なら読み込みは 1 秒前後（NVMe）で、メモリも許容できる。範囲ごとに読む方式は、保存時の置き換えや外部の変更など、考えることが多いので、必要なときだけ使う。C は経路が 1 つになる利点があるが、小さなファイルまでキャッシュ、外部変更の検出、読み取り専用の走査中という制限を持ち込み、普通のファイルが遅く・不便になる。PoC で「全部読む」と「範囲ごと」の開く時間とメモリを比べ、閾値を決め直す。

ADR-0005 の「全部読む場合も、先頭が読めた時点で表示する」は、閾値の下の経路でも別に実装する価値がある（この ADR の範囲外。Phase 6 の PR の 1 つとして足してもよい）。

### 置き場所

閾値は設定ファイルの値。サクラの `nAlertFileSize`（`大きなファイルを開くときの警告`。共通設定の「ファイル」ページ、既定 10MB、1 から 2048）とは別の値で、サクラに無いので、新しい `ume.ini` のキーになる。**ユーザーのデータの形式にあたるので、キーの名前と置き場所は 9 章の質問にする**（案: `[Common]` の `nHugeFileSizeMB`、既定 256、共通設定の「ファイル」ページに数値の入力欄を足す）。

サクラの警告（`nAlertFileSize` 以上で「開きますか？」）は今のまま残す。

## 8. 進め方

### 8.1 PoC と測定

PoC は、`poc/` の捨てる前提の試作ではなく、この ADR が決まった後の最初の PR 群の中で、実際のコードと同じクレートに作る（`Source` の実装が本物になるため）。測る順序は次のとおり。

測るファイル（生成する。10GB は CI に置かず、手元か手動の CI で作る）:

| 名前 | 内容 |
|---|---|
| S1 / S10 | 1GB / 10GB、UTF-8、1 行 40 バイトほど（改行 LF） |
| C10 | 10GB、CRLF |
| T10 | 10GB、1 行 1 バイト（改行だけに近い最悪の例） |
| L1 | 1GB の 1 行（改行なし） |
| J10 | 10GB、Shift_JIS、日本語（全角が多い） |
| W10 | 10GB、UTF-16 LE |
| E1 | 1GB、EUC-JP |

測る項目:

1. 最初の画面が出るまで（目標: 200ms 以内。ファイルの大きさによらない）
2. 走査の時間とスループット（目標: ディスクの読み込み速度の 70% 以上）、走査中の UI の応答
3. 走査中・走査後のメモリ（常駐メモリの目標: ファイルの大きさによらず 300MB 以下。T10 でも）
4. スクロール: 任意の位置へのジャンプと、1 画面の描画（目標: キャッシュが温まっていれば 50ms 以内、冷えていてローカル SSD で 200ms 以内）。Ctrl+End、行番号へのジャンプ
5. 検索: 文字列と正規表現を最初から最後まで（時間、最初の 1 件まで、中断の速さ）。1 スレッドと複数スレッドの比較。`memchr` で絞る案の効果
6. 保存: 10GB を保存する時間、一時ファイルの空き容量、保存後の Undo。同じファイルへの上書き
7. 外部変更: 開いたまま切り詰める、追記する、削除する（Windows・macOS・Linux）。ネットワークドライブ（SMB・NFS）で開く
8. 長い行 L1: 表示、スクロール、編集の応答

確かめる OS の挙動: Windows で、開いたままのファイルの上に rename で置き換えられるか（Rust の版も記録）。Windows の排他ロック（ADR-0010）と読み込みの関係。macOS・Linux で SIGBUS が出ないこと（B 案のため、出ないはずを確かめる）。

測定の結果は、この ADR の「測定の結果」の章（または docs/）に記録して、閾値と大きさ（塊 64KiB、キャッシュ 64MiB、長い行 1MiB）を確定する。

### 8.2 PR の順序（案）

1. `Chunks` を元データの範囲を分けて返すようにする（保存の準備。範囲を読まない今の経路でも動く）。小さな塊の大きさで保存のテストを回す。
2. `RangedFile`（`Source` の実装: 位置指定の読み込み + キャッシュ + 外部変更の検出）と、Grep の巨大ファイル対応（索引を作らず順に読む）。
3. ブロック索引（`LineIndex` の窓口を共通にする）とバックグラウンドの走査（進捗、中断、文字の境界、長い行の目印）。走査中は読み取り専用の文書。
4. UI: 開く経路、閾値の設定、状態表示、概算の行番号、スクロールバー、ジャンプ。
5. レイアウト・色分け・アウトラインの制限（6 章）。
6. 走査後の編集、保存（世代つきの `Store`、空き容量の確認、同じファイルへの上書き）。
7. 検索の最適化（先読み、複数スレッド）、すべて置換の新しいファイルへの書き出し、コピーの上限、パターンのブックマーク。
8. 状態を持つ文字コード（案 B）。必要なら。

各 PR は、前の PR に頼るので順に進める。1 と 2 は別々に進められる。

### 8.3 CI で確かめられること

- 塊の大きさを小さくできる設定（引数）にして、小さなファイルで複数の塊をまたぐ場合を試す（CRLF が塊の境界で割れる、UTF-16 のサロゲートペアが割れる、SJIS の 2 バイトが割れる）。
- 実際のディスクのかわりに、仮想の `Source`（行の番号から内容を計算する）を使い、10GB 相当の走査・索引・検索を、ファイルを作らずに CI で回す（すでに 4GiB 超の位置の試験で同じ方法を使っている）。リリースビルドで数秒から数十秒の見込み。
- 外部変更（切り詰め、追記）は、一時ファイルで CI の全 OS で試せる。
- 実際の 10GB ファイルの測定は CI の通常の経路に入れない。手動で起動する CI のジョブ（`workflow_dispatch`）で、スパースファイルなどを作って測る。ネットワークドライブは手元で測る。
- 人が確かめること: Windows ARM64 の実機（ADR-0009）での体感、ネットワークドライブ、画面のスクロールの滑らかさ。

## 9. 判断してほしいこと（質問）

下の推奨のとおりでよいか、変えるかを教えてほしい。

1. 元データの持ち方: B（位置指定の読み込み + キャッシュ、メモリマップなし）でよいか。
2. 範囲ごとに読むモードの閾値の既定値（推奨: 256MiB）と、設定の名前・置き場所（推奨: `[Common]` の `nHugeFileSizeMB`、共通設定の「ファイル」ページ）。新しい `ume.ini` のキーなので、ユーザーの決定が要る。
3. 走査が終わるまで読み取り専用にしてよいか（推奨: よい。10GB で数秒から数分）。編集したい要望が強いなら、走査済みの先頭部分だけ編集できる形を別に設計する。
4. 外部でファイルが変わったと分かったときに、保存を止めてよいか（推奨: 止める。「名前を付けて保存」と再読み込みだけ許す）。
5. 保存後の Undo: 世代つきの `Store` で残す（推奨）か、保存で Undo の履歴を捨てるか。残すと、履歴が古い版を持つ間、古いファイルの分のディスクを余計に使う（Linux・macOS）。
6. 保存の空き容量が足りないとき、書き始めずに断る（推奨）。それとも同じファイルに直接書く選択肢を出すか（途中の失敗で元のファイルが壊れる。推奨しない）。
7. すべて置換の出力先の名前の決め方（案: ファイル保存のダイアログで聞く）と、結果を自動で開くか。
8. 「すべて選択してコピー」の上限（案: 256MiB）。
9. 状態を持つ文字コード（ISO-2022-JP、UTF-7）の巨大ファイルは、最初は全体を変換して読む（確認を出す）のでよいか。
10. 長い行（案: 1MiB 超）の扱い（区切りで強制的に折り返し、色は付けない）でよいか。
11. アウトライン解析は巨大ファイルでは使えない扱いでよいか。
12. 走査中の概算の行番号の表示（「約」）の書き方。サクラに文言がない表示なので、ADR-0018 の型 F で決めてよいが、巨大ファイル全体の見え方なので、まとめて確認したい。

## 影響

- この ADR が決まったら、ADR-0005 の「残っている確認」（UTF-16 と ISO-2022-JP の範囲の区切り）を、3 章に置き換える。ADR-0005 と ADR-0012 は書き換えず、この ADR から参照する。
- `ume-core` の `Source` / `LineIndex` / `Chunks` の窓口が変わる。コアは UI に依存しない、文書へのアクセスは範囲指定、という [CLAUDE.md](../../CLAUDE.md) の決まりは守る。
- 新しい依存は増やさない（標準ライブラリの `FileExt` を使う。メモリマップを後から足すなら、`memmap2` は MIT / Apache-2.0 で、すでに GPUI 経由で `Cargo.lock` にあるが、直接の依存にするときは別に確認する）。

# ADR-0007: マクロとプラグイン

- 状態: 提案中（Phase 3 の前に確定する。処理系の選び方は PoC で確かめる）
- 日付: 2026-10-08（2026-10-10 にサクラ互換のマクロを足した）

## 要望

- Python や Ruby などの汎用言語でマクロとプラグインを書けるようにしたい
- サクラエディタのマクロもそのまま動かしたい（2026-10-10 に追加）

## 提案

次の 2 本立てにする。どちらも同じ名前付きのコマンドを呼ぶ（[ADR-0008](0008-commands-and-keybindings.md)）。

1. サクラ互換のマクロ: キーマクロ（`.mac`）と JScript（`.js`）を、本体に組み込んだ処理系で動かす
2. 汎用言語のマクロとプラグイン: 別プロセスのプラグインホストと JSON-RPC で通信する

### 1. サクラ互換のマクロ

- 対象はキーマクロ（`.mac`）と JScript（`.js`）。3 つの OS で動かす
- JScript は、Rust から使える JavaScript の処理系（Boa、QuickJS など。どちらも MIT 系のライセンス）を組み込んで動かす。どれを使うかは PoC で決める
- マクロから呼ぶ関数（`Editor.InsText` など）は、サクラのマクロ API の表（`sakura_core/macro/CSMacroMgr.cpp`）に合わせ、名前付きのコマンドにつなぐ
- 対象外: VBScript など WSH の処理系に頼るもの、PPA（`.ppa`）。どちらも Windows の仕組みそのもので、3 つの OS で再現するのが難しい
- サクラの上流には Python のマクロ（`.py`、`sakura_core/macro/CPythonMacroManager.cpp`）もある。互換にするかは、2 の Python 用ライブラリを作るときに決める

### 2. 汎用言語（JSON-RPC）

本体に言語を埋め込まず、別プロセスのプラグインホストと JSON-RPC で通信する（LSP と同じ形）。

- Python と Ruby には、それぞれ小さなクライアントライブラリを用意する
- 利用者が入れたインタプリタと pip / gem の環境をそのまま使う。インタプリタのパスは設定で指定する
- プラグインが落ちてもエディタは落ちない。応答が遅いときはタイムアウトで切り離す
- プラグインホストは、最初に必要になったときに起動する

## 設計の方針

- マクロは「コマンドを順に呼ぶスクリプト」とする。サクラのマクロが F_ コマンドを呼ぶのと同じ考え方で、キーマクロの記録もコマンドの記録で実現する
- API の定義は 1 か所にまとめ、そこから各言語のクライアントを生成する
- 文書へのアクセスは範囲指定で行う（2GB を超えるファイルに対応するため）
- プラグインは、起動のきっかけになるイベント（ファイルを開いた、保存の前など。サクラのジャックに相当）を宣言する。そのイベントが起きるまで起動しない
- キー入力ごと・行ごとに走る処理（色分けなど）はプラグインのコードにさせず、ルールを記述したデータで持たせる

## 見送った案

- Python・Ruby の本体への埋め込み（PyO3 / magnus）: Python と Ruby の実行環境を両方とも同梱・リンクすることになり重い。プラグインが落ちるとエディタも落ちる
- WebAssembly: Python や Ruby をそのままでは使えず、ネイティブ拡張も使えない
- JScript を JSON-RPC 経由で外の処理系（Node.js など）に任せる: サクラのマクロを動かすためだけに、利用者に別の処理系を入れてもらうことになる

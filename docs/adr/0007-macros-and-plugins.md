# ADR-0007: マクロとプラグイン

- 状態: 提案中（Phase 3 の前に確定する。JSON-RPC の形は PoC で確かめる）
- 日付: 2026-10-08（2026-10-10 に、サクラのマクロとの互換と、対応する言語の順番を決めた。2026-10-11 に、JSON-RPC の形と、Emacs Lisp を第 2 弾に加えることを決めた。2026-10-14 に、Lua を試した結果を「第 2 弾の言語で確かめること」に足した）

## 要望

- 汎用の言語でマクロとプラグインを書けるようにしたい
- サクラエディタのマクロでできることは、同じようにできるようにしたい（2026-10-10 に追加）

## 提案

キーマクロだけを本体で動かし、ほかの言語はすべて JSON-RPC で動かす。どちらも同じ名前付きのコマンドを呼ぶ（[ADR-0008](0008-commands-and-keybindings.md)）。

### キーマクロ（`.mac`）

- 本体で動かす。キーマクロの記録も、コマンドの記録で実現する

### JSON-RPC で動かす言語

本体に言語を埋め込まず、別プロセスのプラグインホストと JSON-RPC で通信する（LSP と同じ形）。

- 言語の処理系は同梱しない。利用者が入れた処理系と、そのパッケージの環境（pip など）をそのまま使う。処理系のパスは設定で指定する
- 各言語から呼ぶための小さなライブラリは、エディタに同梱する
- プラグインが落ちてもエディタは落ちない。応答が遅いときはタイムアウトで切り離す
- プラグインホストは、最初に必要になったときに起動する

通信の形（2026-10-11 にユーザーが承認。仕様の案と試した結果は [docs/poc/json-rpc.md](../poc/json-rpc.md)）:

1. 標準入出力を使う
2. `initialize` で情報（プロトコルの版、プロセス ID、エディタの名前と版、文書のパスなど）を渡す
3. ASCII で 1 行 1 メッセージにする（改行は LF だけ。ASCII 以外は `\uXXXX` で書く）
4. 基本 API を前もって作る（定義を 1 か所に書き、言語ごとの関数を生成する）
5. マクロ（1 回走って終わるもの）とプラグイン（常駐してイベントを受けるもの）を分ける。この形はマクロだけを扱い、プラグインは別の形で後で決める

利用者のスクリプトには `require` や `import` を書かせない。言語ごとの起動の仕組みで、ブートと基本 API を先に読み込む。

対応する順番:

| 順番 | 言語 | 備考 |
|---|---|---|
| 初期実装 | JavaScript（サクラの JScript マクロの代わり）、Python | JavaScript の処理系は Node.js を基本にする |
| 第 2 弾 | PowerShell、AppleScript、PHP、Ruby、Lua、VBScript、Emacs Lisp | 利用者が処理系を入れれば動く形にする。Emacs Lisp は `emacs -Q --batch` で動かし、Emacs 30 以降を対象にする（2026-10-11 にユーザーが決めた） |
| 第 3 弾 | コンパイルする言語 | 必要になったら決める |

### サクラのマクロとの互換

- サクラのマクロでできることは、同じようにできることを目指す。マクロから呼ぶ関数の名前と引数は、サクラのマクロ API の表（`sakura_core/macro/CSMacroMgr.cpp`）に合わせる
- ソースのままでの互換は求めない。サクラの JScript や VBScript のマクロは、生成 AI で書き換えれば動く程度の互換でよい
- PPA（`.ppa`）は対象外
- サクラの上流の Python のマクロ（`.py`、`sakura_core/macro/CPythonMacroManager.cpp`）も、同じ考え方で扱う

### 第 2 弾の言語で確かめること

- Emacs Lisp
  - Emacs 30 以降を対象にする（JSON の関数が本体に入ったのが 30 から）
  - `emacs -Q --batch` で、利用者の設定を読まずに起動する
  - ブートが利用者のファイルを 1 式ずつ読んで評価し、エラーに行番号が出るようにする（`-l` で読むと出ない）
  - 文字コードは UTF-8 に固定する
  - エディタから送る行は LF だけにする（Linux の Emacs は CRLF で読み取りに失敗した）
- Lua（2026-10-14 に試した。[docs/poc/json-rpc.md](../poc/json-rpc.md) の「Lua」）
  - Lua 5.1（LuaJIT）から 5.5 までを対象にする。ブートはビット演算と utf8 ライブラリを使わずに書き、どの版でも動くようにする
  - 標準ライブラリに JSON がないので、ブートに書く
  - 利用者のスクリプトは、エディタが名前と中身を `initialize` で渡し、ブートが `load` で読む。Windows の lua.exe はファイルを ANSI の API で開くので、パスを引数で渡すと、CP932 にない文字のパスを開けない
  - 処理系を同梱するかは決めていない（json-rpc.md の「決まっていないこと」）
- AppleScript は標準入出力で JSON-RPC を話すのが難しいので、`osascript` を呼ぶ小さな中継が要る見込み
- VBScript は、Microsoft が廃止を予定している。Windows で使える間だけの対応になる

## 設計の方針

- マクロは「コマンドを順に呼ぶスクリプト」とする。サクラのマクロが F_ コマンドを呼ぶのと同じ考え方で、キーマクロの記録もコマンドの記録で実現する
- API の定義は 1 か所にまとめ、そこから各言語のクライアントを生成する
- 文書へのアクセスは範囲指定で行う（2GB を超えるファイルに対応するため）
- プラグインは、起動のきっかけになるイベント（ファイルを開いた、保存の前など。サクラのジャックに相当）を宣言する。そのイベントが起きるまで起動しない
- キー入力ごと・行ごとに走る処理（色分けなど）はプラグインのコードにさせず、ルールを記述したデータで持たせる

## 見送った案

- Python・Ruby の本体への埋め込み（PyO3 / magnus）: 実行環境を同梱・リンクすることになり重い。プラグインが落ちるとエディタも落ちる
- JavaScript の処理系（Boa、QuickJS など）の本体への組み込み: サクラのマクロとの互換は、生成 AI で書き換えれば動く程度でよい。すべての言語を JSON-RPC にそろえると、作りが 1 つで済み、本体も軽くなる。代わりに、JavaScript を使う人は Node.js などを入れる必要がある
- WebAssembly: Python や Ruby をそのままでは使えず、ネイティブ拡張も使えない

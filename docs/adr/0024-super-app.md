# ADR-0024: タブにエディタ以外の機能を入れる（スーパーアプリ化）と、メニューの切り替え・アイコン

- 状態: 決定（2026-10-24 にユーザーが、下の「決めたこと」の 9 項目をすべて推奨どおりに決めた）
- 日付: 2026-10-24（ユーザーが「タブの中にエディタ以外の機能を組み込む、スーパーアプリ化が技術的にできるか検討。メニューアイコンやメニューの切り替えも検討」と頼んだ）

下調べの詳細（コードの場所、各候補のライセンスと難しさ、確かめていないこと）は [docs/poc/super-app.md](../poc/super-app.md)。

## 背景

MATSU Editor はサクラエディタの操作感を再現するテキストエディタで、サクラの機能を埋める作業が続いている（[roadmap](../roadmap.md)）。そこへ、端末・結果の表・プレビューなどエディタ以外の物をタブに入れる案が出た。MATSU が「テキストエディタ」を超えるかどうかは、製品の方向の判断で、AI が決めてよい範囲（[ADR-0018](0018-decision-policy.md)）ではない。この ADR は、できるか・どれだけかかるか・何が危ないかを調べ、推奨を付けて、ユーザーに選んでもらうための下書きである。

## 調べた結果

### できるか

できる。ただし順番が要る。

- 今のタブは、中身が `PaneSet`（最大 4 つの `EditorView`）と決まっている（[ADR-0015](0015-tabs-and-groups.md)、`crates/matsu-ui/src/tabs/`、`panes/`）。エディタ以外を入れるには、タブの中身を「エディタ」か「パネル」の列挙型にする。これが最初の関門で、`tabs/`、`file_ops/windows.rs` と `close.rs`、`app.rs` の描画、`menu_state.rs` に及ぶ。PR 3〜5 本
- 実行する関数は `EditorView::run_function` に集まっていて、UI コマンドは `&mut EditorView` を受ける。エディタ以外のタブでは、編集の関数を「使えない（灰色）」にすれば、そのコマンド側（約 730 行）は変えなくてよい。ただし新規・開く・閉じる、タブやウィンドウの関数も `EditorView` を受けるので、非エディタのタブから呼べる道（`Workspace` 経由）の洗い出しと追加が要る
- エディタ以外の物は、今もウィンドウに付くパネルとして入っている（検索、Grep、DIFF、アウトライン、ファイルツリー）。サクラはそれらを文書やパネルで見せるので、サクラの機能のために新しいタブは要らない。タブにする理由は、サクラにない機能（端末など）だけ

### メニューのアイコン

- Windows と Linux: **すでに出る**。MATSU がメニューを自分で描き（GPUI にこの 2 つの OS のメニューはない）、サクラの「アイコン付きメニュー」（`bMenuIcon`）に従っている（`menu_icons.rs`）
- macOS: 出ない。OS のメニュー（`NSMenu`）を GPUI が作るが、GPUI の `MenuItem` が画像を持たず、作る処理も `setImage` を呼ばない
  - 方法 A: GPUI の 2 つのクレート（`gpui-pre`、`gpui-pre-macos`。Apache-2.0）を写しで差し替え、`MenuItem` に画像を足す。改めたと書けば Apache-2.0 で許される。週ごとの版上げのたびに当て直す手間が残る。Zed に PR を出す道もあるが、ほかの OSS への報告のルールに従う
  - 方法 B: GPUI は直さず、`cx.set_menus` の直後に `matsu-platform`（すでに `objc2-app-kit` の `NSMenu`・`NSMenuItem` を使っている）が `NSApp.mainMenu` を歩いて、`NSMenuItem::setImage` を付ける。GPUI の `tag` は作り直すたびに増える数なので使わず、メニューの木の形で項目と結ぶ。gpui-component の `native_menu/macos.rs`（Apache-2.0）に同じ呼び出しの見本がある。**読んだだけで、動かしていない**

### メニューの切り替え

ユーザーの言い方は 2 通りに読める。どちらの意味か、ユーザーに聞く。

- 読み方 1（タブの種類で変わる）: Windows と Linux は、メニューバーがアプリで 1 つの一覧を読む作りを、アクティブなタブの種類の一覧を読む作りに変える。macOS は、ウィンドウがアクティブになったときにメニューを作り直す仕組み（`refresh_menu_states`）がすでに動いているので、タブの切り替えでも呼べばよい。どちらも小さい。大きいのは、エディタ以外の種類のメニューの中身を決めること
- 読み方 2（利用者がセットを選ぶ）: 自分でメニューを作る土台（`[MainMenu]`）はできている。組み込みのセット（サクラの既定、簡単なメニュー）を数個持ち、選んだ名前を覚えるだけで足りる。小さい
- 2 つは両立する。サクラの互換のため、エディタのタブのメニューと `[MainMenu]` の読み方は変えない

### エディタ以外のタブの候補

詳細は調べの 4 章。

| 候補 | 難しさ | 新しい依存 | 向き |
|---|---|---|---|
| Markdown / HTML のプレビュー | 小 | なし（gpui-component の `TextView`） | 最初の 1 つに向く |
| 画像ビューアー | 小 | なし | 文書でないファイルを開く道が要る |
| 結果の表（データベース） | 中 | なし（gpui-component の `DataTable`） | ADR-0023 と一緒に考える |
| DIFF の並べた表示 | 中 | なし | 新しい描画が要る |
| ターミナル | 大 | `alacritty_terminal`（Apache-2.0） | 「スーパーアプリ」らしさの中心。描画と入力は自前 |
| Web ビュー | 大 | `wry`（Apache-2.0 OR MIT）。Linux は WebKitGTK（LGPL）に結び付く | 優先しない（下） |
| ヘルプ・設定のタブ化 | 小〜中 | なし | 価値は小さい |

- ターミナルは、`alacritty_terminal` が端末の状態と子プロセスの起動（PTY と ConPTY）を持つ。Zed のターミナルのクレートは GPL なので読まない。最小で PR 5〜8 本
- Web ビューは、`wry` の Linux 版が、窓のハンドルから作る場合は X11 だけで、Wayland は GTK のコンテナが要る（wry 0.57.1 の説明）。GPUI は GTK ではないので、Wayland では置けない。X11 は GPUI との組み合わせを確かめていない。Linux の共有ライブラリが LGPL であることは、「GPL 系の依存を使わない」ルールにどう当たるか、ユーザーの判断が要る
- プラグインがタブの中身を出すのは、プラグイン（常駐する形）の ADR が決まったあと。MATSU が描く宣言的な画面（JSON）が現実的で、費用は中〜大。公開の API になるので、タブの約束が安定してから決める

### リスク

- 範囲と手入れ: サクラの機能を埋める作業と同じファイルを触る。ターミナルは小さくならない
- アクセシビリティ: エディタの本文もまだ読み上げに出ていない。新しい中身は名前と役割から始める
- サクラの互換: エディタのタブの動きと設定の読み方は変えない。新しいものはサクラにない節に書く
- 文書を読むタブ（プレビュー）は、文書への範囲指定のルール（CLAUDE.md）に合わせる必要がある。`TextView` は文字列を受けるので、上限か見えている範囲だけを渡す決めが要る
- エディタの性能: 描画の経路は共有しない。ターミナルは読み取りを別スレッドにする
- 配布物の大きさ: 測っていない（実装するときに測る）

## 推奨

作るなら、次の順にする。どの段階でも止められる。

1. 今は作らず、方向だけ決める（この ADR を決定にする）
2. **メニューのアイコン（macOS）**: 方法 B。Windows と Linux はすでに出ている。ほかの話から独立していて、小さい。先に macOS で 1 項目を試す
3. **タブの抽象化**: 中身を列挙型にし、パネルの約束（表題、閉じる確認、フォーカス、メニューの種類、ステータス、アクセシビリティの名前）を決める。中身はまだエディタだけで、見た目は変えない
4. **メニューの切り替え（読み方 1）**: 3 の上に載せる。読み方 2 は、ユーザーが望むなら独立に作れる
5. **最初のエディタ以外のタブ**: Markdown / HTML のプレビュー（依存が増えず、約束を試せる）
6. **次の種類**: 結果の表（ADR-0023 の方針に合わせる）、画像、ターミナルの順に、1 つずつ別の ADR か PR で決める。ターミナルは依存が増え、描画と入力が大きいので、5 までを作って約束が合っていると分かってから
7. Web ビューは作らない。外部のブラウザで開く道（`shell`）で足りるかを先に見る
8. プラグインのタブは、プラグインの ADR のあと

PR の順: ア) アイコン（macOS）→ イ) タブの抽象化（複数 PR）→ ウ) メニューの切り替え → エ) プレビューのタブ。ア）はイ）と無関係なので、並行して進められる。

## 決めたこと

2026-10-24 に、ユーザーが 9 項目をすべて推奨どおりに決めた。

1. **広げる範囲**: MATSU をテキストエディタの外へ広げる。ただし「推奨」の 3〜5（タブの約束を作り、小さい 1 つのタブまで）まで。ターミナル以降は、そこまで作った結果を見てから決める
2. **メニューの切り替え**: タブの種類で変わる（読み方 1）。「推奨」の 3 とそろえて作る。利用者がセットを選ぶ読み方 2 は、望まれたら別に
3. **macOS のメニューアイコン**: 方法 B（GPUI を直さず、`cx.set_menus` の後に `matsu-platform` で `NSMenuItem::setImage`）。方法 A と Zed への PR は、B で足りないと分かってから
4. **最初のエディタ以外のタブ**: Markdown / HTML のプレビュー
5. **ターミナル**: 「推奨」の 5 の結果を見てから、別の ADR で決める（依存 `alacritty_terminal` の追加と安全の扱いもそこで）
6. **Web ビュー**: 作らない。LGPL の共有ライブラリに結び付く物の扱いは、作らないので決めない
7. **`matsu.ini` の新しい設定**: サクラにない節にまとめ、サクラの節は変えない
8. **プラグインのタブ**: プラグインの ADR（ADR-0007 の常駐する形）が決まってから
9. **エディタ以外のタブの閉じ方**: タブの約束に「閉じる確認」を入れ、種類ごとに決める

## 見送った案

- 最初からプラグインのタブにする案: 約束が固まる前に公開の API を作ることになる
- Web ビューをタブの基盤にする案: Linux の Wayland で置けず、LGPL の共有ライブラリに結び付き、描画が GPUI と別になる
- 別のアプリ（端末アプリなど）に分ける案: タブやメニューの切り替えという要望に答えない。ただし、広げる範囲が大きくなりすぎるときの退路としては残る

## 影響（決めたときに変わるところ）

- `crates/matsu-ui/src/tabs/`、`panes/`、`app.rs`、`file_ops/windows.rs` と `close.rs`、`menu_state.rs`、`menu_bar.rs`、`status_bar.rs`
- macOS のメニュー: `crates/matsu-platform`（`objc2-app-kit` の `NSImage` の feature を足す）
- ADR-0015（タブ）は、中身が「エディタ」だけでなくなる点を追記する。コアと UI の依存の向き（[ADR-0013](0013-module-structure.md)）は変わらない。端末やプレビューは UI の側に置く

## 確かめてほしいこと（Windows と macOS）

調べでは試作を作らなかった。実装の前に確かめるなら、[調べ](../poc/super-app.md#windows-と-macos-で確かめること)の末尾の 4 つ。とくに、macOS で `NSMenuItem::setImage` が `cx.set_menus` の後で効くか、メニューを作り直しても残るか。

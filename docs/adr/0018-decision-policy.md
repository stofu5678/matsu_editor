# ADR-0018: 判断の方針（AI が決めてよいことと、人に聞くこと）

- 状態: 決定
- 日付: 2026-10-21（ユーザーが「AI にもっと任せる進め方」を探ることにし、その案の 1 つとして下書きを頼み、同じ日に決めた）。同じ日に、型 A を保存の結果やマクロの結果が変わるものにも広げた（「追記」）

## 背景

ADR-0014 で、Phase 5 からは AI が実装・テスト・レビュー・マージを繰り返し、人は次だけを判断すると決めた。

- ADR の変更
- 依存の追加
- データが消えるおそれのある処理

ループの細かいルールは `CLAUDE.md` に書くことにしたが、まだ書いていない。

2026-10-16 から、ラウンドごとに 5〜8 のエージェントが並行して PR を作っている。各 PR の「判断してほしいこと」にはユーザーがチャットで答え、ユーザーが結果を見てマージしている。ラウンドが進むにつれて、判断を待つ時間と、答えるユーザーの手間が増えた。

2026-10-21 までの「判断してほしいこと」を数えると、「なし」でないものが 98 の PR に 172 件あった。

- 答えの記録があり、推奨も書かれていたのは 30 件である。そのうち 7 件で、ユーザーは推奨と違う形を選んだ。7 件のうち 2 件は、前提の誤りを直したものである（AI がユーザーの答えを読み違えた ADR-0008 の Mac のキーと、ファイルの大きさの上限の ADR-0012）。
- 93 件は、答えの記録がないままマージされた。推奨どおりと見られるが、チャットで直されたものもあり得る。

推奨と違う形になったものは、次の 2 つの型に集まっていた。

- **サクラの不具合や効かない設定を写すか、ちゃんと動かすか。** ユーザーは動かすほうを選んだ（#93 の DIFF の「差分なし」のメッセージ、#117 の HTML のアウトライン）。ファイルの大きさにも、64 ビット版のサクラと同じく上限を設けないことにした（ADR-0012）。
- **範囲を広げる。** スクリプトから呼べる UI コマンドを全部にした（#97）。タイプごとのタブ幅と空白の挿入を足した（#113、#120、#166）。

ライセンスでは、推奨が覆った記録はない。ユーザーはルールを足す側だった（MPL-2.0、bregonig、Bison の例外、wayland のプロトコルの定義、サクラの古い著作権の文言）。

AI の側の誤りもあった。ユーザーの答えを読み違えたもの（ADR-0008）と、サクラの挙動を読み違えたもの（#143、#155、#157。コーディネーターがレビューで見つけて直した）である。

## 決定

### 1. AI が決めて進めてよいこと

次の型に当てはまる判断は、担当（エージェント）が決めて進める。PR の「判断したこと」に、型と理由を書く。

| 型 | 決め方 |
|---|---|
| A. サクラの明らかな不具合・効かない設定 | 正しく動く形にする。保存したファイルの中身やマクロの結果が変わるものも含む（「追記」）。不具合と決める前に、サクラのソースで理由を確かめ、マクロが頼っている動きは不具合として扱わない。サクラとの違いを、コードのコメントと PR に書く |
| B. OS や GPUI でサクラどおりにできない | いちばん近い形にする。できないことと代わりの形を PR に書く |
| C. 画面の細部やタイミングの違い | サクラに合わせる。合わせられないときは B にする |
| D. 範囲（見送り・後回し） | 足りない土台が要るものは見送る。「残っていること」に理由とともに書き、コーディネーターが次の候補に集める |
| E. CI の手間 | 1 つのジョブが 20 分ほどまでで、ほかのジョブと並行して動くなら決めてよい |
| F. サクラに文言がない表示の言葉 | `CLAUDE.md` の名前のルールに従って決める |

### 2. 人に聞くこと

次は AI が決めない。PR の「判断してほしいこと」に書いて、ユーザーの答えを待つ。

- ライセンスと依存: 依存の追加、新しい種類のライセンス、ほかのプロジェクトのコードの写し
- ADR の追加と変更
- 利用者のデータ: 保存・バックアップ・削除の処理、`ume.ini` の形式と置き場所（サクラとの互換）
- セキュリティ: 外部のプログラムの実行、ネットワーク、権限
- リリース: 版の番号、署名、公開、リポジトリの設定と secret
- ほかの OSS への投稿（`CLAUDE.md` の「ほかの OSS への報告」）
- 結果が変わるサクラとの違い: 保存したファイルの中身や、マクロの結果が変わるもののうち、型 A に当てはまらないもの（サクラの不具合ではなく、別の形を選ぶもの）
- ユーザーが前に決めたことを変えるもの
- どの型に当てはまるか迷うもの

### 3. 残し方と見直し

- PR の本文は、「判断したこと」（型と理由）と「判断してほしいこと」（2 の項目だけ）に分ける。
- コーディネーターは、PR を確かめるときに、型の当てはめが正しいかも見る。サクラの挙動についての主張には、ソースの場所か、サクラ本体で確かめた結果を添える。
- ユーザーは、「判断したこと」をいつでも覆せる。覆したときは、直す PR を作る。コーディネーターの作業の記録には、どの型の判断が覆ったかを残す。
- ある型の判断が何度も覆るときは、その型を「人に聞くこと」に移す。

### 4. この ADR で決めないこと

PR のマージは、これまでどおりユーザーが行う。ADR-0014 の自動のマージは、始める時期と条件を別に決める。第 13 ラウンドで作る自動の確認（画面の撮影、サクラ本体との比較）ができてから決める。

## 実施の時期

この ADR が決まったら、`CLAUDE.md` に「判断の方針」の節を足す（この ADR と同じ PR に入れる）。エージェントへの指示書の共通部分も、同じ形に直す。

## 追記（2026-10-21）: 型 A を、結果が変わるものにも広げる

サクラ本体と UME に同じキーマクロを流して保存の結果を比べるテストを 449 件に広げたところ、違いが 26 件見つかった。そのうち 3 件はサクラの不具合のように見えたので、写すかどうかをユーザーに聞いた。ユーザーの答えは次のとおり。

> いずれもサクラエディタの仕様に合わせるべきではないと判断します。より良い仕様があればそのように実装してください。本プロジェクトはまだほぼ未公開の状態で既存のユーザーがいませんのであえてバグっぽい旧仕様を残す意味はありません

これを受けて、次のように決めた（ユーザーが了承）。

- 型 A は、保存したファイルの中身やマクロの結果が変わるものにも当てはめる。サクラの不具合のような動きは、保存の結果が変わっても、写さずに正しく動く形にする。
- ただし、不具合と決める前に、サクラのソースで理由を確かめる。3 件のうち 1 件（すべて選択のあとに次を検索して見つからないと、選択が消える）は不具合ではなかった。サクラは検索の前にかならず選択を外す（`sakura_core/cmd/CViewCommander_Search.cpp` の `Command_SEARCH_NEXT`、「現在の選択範囲を非選択状態に戻す」）。マクロの `S_SearchNext` は結果を返さないので、検索のあとに選択があるかどうかが、見つかったかどうかの合図になる。コーディネーターがソースを読んで見誤りに気づき、ユーザーはサクラの動きに合わせることを選んだ。このように、マクロが頼っている動きは不具合として扱わない。
- サクラと違う形にしたものは、比較のテストの許可リスト（`crates/ume/tests/sakura_oracle/known_differences.txt`）に理由とともに残す。

## Claude Code が気づいたこと

手順を書くときと、ドライランで気づいたもの。どれも、ユーザーが手順で確かめる。ドライランの値は、2026-10-11 にこの PC で 1〜8 回測ったもの。

- 機種: コメントは「Surface-class」と書いたが、`Win32_ComputerSystem` では「Dell Inc. / XPS 13 9345」だった（手順 1）。issue を立てた人の PC（Surface Laptop 7th gen）と同じ GPU という意味で書いたのかもしれない（推測）が、Surface と読める
- 書き込みごとの増え方: コメントは「every `UpdateSubresource` into that texture adds exactly +4.0 MB」と書いたが、ドライランの試作では、148〜149 回の書き込みのうち、最初の 64 回は約 4 MiB ずつ増え、65 回目は約 0.8 MiB、66 回目からは、ほとんどが 0 だった（4 回とも同じ。`update1` の 3 回も同じ）。KiB で測った 3 回では、約 4 MiB の増え方は 4108〜4116 KiB（ちょうど 4 MiB より 12〜20 KiB 多い）だった。最小のウィンドウ（9 回。日本語の行ありで 25 回）では、どの書き込みでも約 4 MiB 増えた。グレースケールの試作（148〜149 回、2 回）では、どの書き込みでも約 1 MiB（KiB で測った 1 回では 1028〜1064 KiB）増えた（手順 7）
- `Flush()`: コメントは「効かなかった」と書いたが、ドライランでは、書き込みのたびに `Flush()` を呼ぶと、試作の 6 秒後のワーキング セットが約 307〜314 MB から 68〜136 MB に減った（8 回。うち計測を止めた 3 回は 80 MB、93 MB、136 MB）。減り方は、回によって大きく違った。`UpdateSubresource1` と `D3D11_COPY_NO_OVERWRITE` は、コメントのとおり変わらなかった（手順 7）
- 内訳の表示: コメントの「~4 MB private allocations: 61 of them」は、memstat では `5 MB x 61` と出る。memstat は確保の大きさを MB に切り上げて数えるので、4 MB を少しでも超える確保は、5 MB の行に入る（手順 4）
- 変更の範囲: コメントは「limited to `DirectXAtlasTexture::upload`」と書いたが、パッチは、`upload` に `device` を渡すための呼び出し側の 1 行（`insert` の中）と、`use` の行も変えている（手順 6）
- 原因の書き方: 回避策のパッチの中のコメントと、2026-10-09 の記録は、原因をドライバーと言い切っている（「make a full copy of the destination texture for every `UpdateSubresource` call」）。この手順で確かめられるのは、書き込みの呼び方とメモリの増え方の関係までで、ドライバーやランタイムの中で何が起きているかは分からない
- ほかの GPU: 2026-10-10 に、x64 の Windows の NVIDIA GeForce GTX 1650 と Mac では起きなかった（[結果](../poc/ui-framework-result.md)。AI が測った値）。コメントの最後の文は、その前に書いた

### 計測の関数

PowerShell のウィンドウを開くたびに、1 回貼り付ける。

```powershell
function Measure-Poc {
    param(
        [Parameter(Mandatory = $true)][string]$Exe,
        [hashtable]$Vars = @{},
        [int[]]$At = @(6),
        [switch]$Keep
    )
    $global:PocId = $null
    Get-ChildItem Env:POC_* | Remove-Item
    foreach ($name in $Vars.Keys) { Set-Item "Env:$name" "$($Vars[$name])" }
    try {
        $p = Start-Process -FilePath $Exe -WorkingDirectory $PWD -NoNewWindow -PassThru -ErrorAction Stop
    } finally {
        foreach ($name in $Vars.Keys) { Remove-Item "Env:$name" }
    }
    $global:PocId = $p.Id
    $elapsed = 0
    foreach ($t in $At) {
        Start-Sleep -Seconds ($t - $elapsed)
        $elapsed = $t
        $p.Refresh()
        if ($p.HasExited) { throw "the process exited before $t s" }
        '{0,3} s: working set {1,6:N1} MB, private {2,6:N1} MB' -f $t, ($p.WorkingSet64 / 1MB), ($p.PrivateMemorySize64 / 1MB)
    }
    'process ID {0}' -f $p.Id
    if (-not $Keep) {
        [void]$p.CloseMainWindow()
        if (-not $p.WaitForExit(3000)) { Stop-Process -Id $p.Id }
    }
}

function Open-PocFile([string]$Name) {
    $path = Join-Path $PWD "$Name-$PocId.txt"
    if (-not (Test-Path $path -PathType Leaf)) { throw "$path does not exist" }
    Invoke-Item $path
    $path
}
```

`Measure-Poc` は、起動して、決まった秒数の後のメモリを出す。

- `POC_` で始まる環境変数を消し、`@{ ... }` で渡したものだけを付けて起動する。作業フォルダーは、今いるフォルダー。試作が出す `first frame: ... ms` の行（最初の描画までの時間）も、同じウィンドウに出る
- 起動から `-At` の秒数（既定は 6 秒）が経ったら、ワーキング セット（`working set`）とプライベート バイト（`private`）を出す。どちらも `Get-Process` と同じ、Windows が数えた値。タスク マネージャーの「詳細」タブでは、「ワーキング セット (メモリ)」と「コミット サイズ」の列にあたる。既定で出ている「メモリ (アクティブなプライベート ワーキング セット)」とは別の値なので、比べない。秒数は、起動してから待った時間で、目安
- MB は 1024 × 1024 バイト（MiB）。タスク マネージャーと同じ
- 起動したプロセスの ID を `$PocId` に入れる
- 測り終わったらウィンドウを閉じる（閉じなければ止める）。`-Keep` を付けると、開いたままにする
- 起動できなかったときと、測り終わる前にプロセスが終わったときは、赤い文字のエラーを出して止まる

`Open-PocFile` は、直前に `Measure-Poc` で起動したプロセスが書いたファイル（`memstat-<プロセス ID>.txt` か `atlas-<プロセス ID>.txt`）を、テキスト エディター（既定ではメモ帳）で開き、そのパスを返す。ファイルがなければ、エラーを出して止まる（前のプロセスのファイルを開かないため）。

## 手順 4: メモリの内訳（主張 2）


`POC_MEMSTAT=6` を付けると、試作は起動して 6 秒後に、メモリの内訳を今いるフォルダーの `memstat-<プロセス ID>.txt` に書く（`src\memstat.rs`。これも AI が書いたコード）。見るところは次のとおり。

| 行 | 何の値か | コメントの値 |
|---|---|---|
| `rust heap live` | Rust が確保して、まだ返していない量。全体のアロケーターを包んで数える | 約 3 MB（2026-10-09 の記録では 2.7 MB） |

## 手順 6: 回避策のパッチ（主張 6、主張 7 の右の列）

### パッチを読む

`C:\work\ume-97908ca\poc\gpui-textview\patches\gpui-pre-windows-atlas-upload.diff` を開く。コメントのリンク先と同じ中身。

- `UpdateSubresource` の代わりに、`D3D11_USAGE_STAGING` のテクスチャを作り、`Map` / `Unmap` で書いて、`CopySubresourceRegion` でアトラスに写しているか
- 変更が `DirectXAtlasTexture::upload` に収まっているか（上の「Claude Code が気づいたこと」）
- アトラスの割り当てや、キャッシュのキーを変えていないか（「atlas semantics are unchanged」）。CPU 側にアトラスの写しを持ったり、書き込みをまとめたりしていないか
- パッチの中のコメントは、原因をドライバーと言い切っている。手順で確かめられるのは、書き込みの呼び方とメモリの増え方の関係まで（上の「Claude Code が気づいたこと」）

### 当てる

```powershell

Copy-Item $src C:\work\gpui-pre-windows-0.3.8-fix -Recurse

```

- `$src` は、手順 2 のビルドで crates.io から取ってきた GPUI の Windows 部分（`gpui-pre-windows` 0.3.8）
- `Applied patch src/directx_atlas.rs cleanly.` と出るか
- 写しは、リポジトリの外に置く。git のリポジトリの中で `git apply` すると、パッチのパスをリポジトリの最上位から数えるので、当たらずに飛ばされる
- やり直すときは、先に写しを消す（`Remove-Item C:\work\gpui-pre-windows-0.3.8-fix -Recurse -Force`）。残っていると、`Copy-Item` は写しの中にもう 1 つ写しを作り、パッチは当たらない（当て済みのため）


- 出力に `Compiling gpui-pre-windows v0.3.8 (C:\work\gpui-pre-windows-0.3.8-fix)` の行があれば、パッチを当てた写しが使われている

### 試作の書き込みを見る（主張 2・3）

内訳（手順 4）と同じプロセスで見るため、`POC_MEMSTAT` も付ける。

```powershell
Measure-Poc .\target-diag\release\gpui-textview-poc.exe @{ POC_MEMSTAT = 6 } -At 8
Open-PocFile atlas
Open-PocFile memstat
```

行の形は次のとおり（値は例）。最初の列は、最初の行からの秒数。

```text
   0.000 s  texture Subpixel[0] created: 1024x1024 R8G8B8A8_UNORM, 4096 KiB; private 59.3 -> 63.3 MB (+4124 KiB)
   0.001 s  upload method: UpdateSubresource
   0.001 s  upload 1 to Subpixel[0] with UpdateSubresource: 13x16 at (768, 0); private 63.3 -> 67.3 MB (+4108 KiB, sum 4.0 MB)
```

- `texture`: テクスチャを作った。種類と番号、大きさ、形式、テクスチャの大きさ（KiB）と、作る前後のプライベート バイト、その差（KiB）
- `upload method`: `POC_ATLAS_UPLOAD` で選んだ呼び方
- `upload <番号>`: テクスチャに 1 つ書き込んだ（文字の形など）。`with` の後が、実際に呼んだ関数。書き込んだ場所、呼ぶ直前と直後のプライベート バイト、その差（KiB）、`sum` はここまでの差の合計。合計は、呼んでいる間の差だけを足したもの。呼び出しと呼び出しの間に増えたり減ったりした分は入らず、ほかのスレッドが同じ間に確保した分は入る
- プライベート バイトを取れなかったときは、値が `?` になり、合計に `without <回数> unknown`（その回数の分は入っていない）が付く。ドライランでは出なかった。出たら、その回の合計は正しくないものとして扱う

| 見ること | コメントの主張 |
|---|---|
| `texture` の行が 1 つだけで、`Subpixel[0]`、`1024x1024 R8G8B8A8_UNORM, 4096 KiB` か | 「Only one atlas texture is created (Subpixel, 1024x1024 RGBA = 4 MB)」 |
| どの `upload` の行も、約 4 MB（4096 KiB 前後）増えているか。ちょうど 4096 KiB か | 「every `UpdateSubresource` into that texture adds exactly +4.0 MB」 |
| 約 4 MB 増えた `upload` の行の数と、その合計が、同じプロセスの memstat の約 4 MB の確保（`5 MB x` の行）と合うか | 主張 2（61 個、約 244 MB）。ただし、確保の数え方が違うので、一致しなくてもおかしくはない。近いかを見る |

書き込みの数と、増え方ごとの行の数は、次のように数えられる。

```powershell
(Select-String -Path "atlas-$PocId.txt" -Pattern 'upload \d+ to').Count
Select-String -Path "atlas-$PocId.txt" -Pattern 'upload \d+ to .*\(([+-]\d+|\?) KiB,' | ForEach-Object { $_.Matches[0].Groups[1].Value } | Group-Object -NoElement | Sort-Object Count -Descending
```

2 つ目は、`Count`（行の数）と `Name`（増えた KiB）の表を出す。例えば `Count` が 10、`Name` が `+4108` の行は、4108 KiB 増えた書き込みが 10 回あったということ。`Name` が `?` の行は、プライベート バイトを取れなかった書き込み。`Count` を足すと、1 つ目の数になる。

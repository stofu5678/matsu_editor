# 通常の文書の、とても長い行の中でのキーの重さ（測定）

1 行が数十〜数百 MiB ある文書を、**通常の文書**（`nHugeFileSizeMB` 未満なので、範囲ごとではなく全部を読む）として開いたとき、その行の中でキーを押すと何が、どれだけ重いかを測った記録。測るだけで、動作は変えていない。直し方は、この数字を読んだユーザーが決める（2026-11-28 に「まず原因を測ってから決める」と決めた）。

- 測るプログラム: `crates/matsu-ui/src/view/long_line_measure.rs`（窓を開かない。GPUI の `TestAppContext`。`#[ignore]`なので CI では動かない）
- 数える仕掛け: `crates/matsu-core/src/measure.rs`（`measure` 機能をつけたときだけ入る。つけないビルドでは中身が空で、製品の動きも速さも変わらない。ワークスペースのどのビルドもつけない）

## 動かし方

```sh
cargo test --release -p matsu-ui --features measure --lib -- \
    --ignored --nocapture --test-threads=1 long_line_measure_
```

- 1 つの長さだけなら、名前を `long_line_measure_16_mib` のようにする（4・16・64・200 MiB がある）。`--test-threads=1` は、常駐メモリ（プロセス全体の値）を、ほかのテストと混ぜないため。
- リリースビルドで測る。デバッグビルドでは遅すぎて、数字が参考にならない。
- 時間: ビルドのあと、4 MiB で約 2.5 秒、16 MiB で約 5 秒、64 MiB で約 30 秒、200 MiB で約 85 秒（この機械）。
- `MATSU_LONG_LINE_ROUNDS`（既定 3）は、同じ手順を繰り返す回数。表は、各部分でいちばん速かった回の数字。`MATSU_LONG_LINE_MIN_US`（既定 100）は、「下の層」の表に載せる最小の時間（マイクロ秒。0 で全部）。
- `--features measure` をつけないと、数え役（下の層の表）が入らず、時間と常駐メモリだけが出る。

## 何を測ったか

文書は「`first line`」の行、`0123456789abcdef` を繰り返した ASCII の 1 行（4・16・64・200 MiB）、短い 4 行。Sandbox の測定（200 MiB の行 1 本、全体 209.7 MB）と同じ形。ファイルは一時フォルダに書いて、`open_file` で開く（アプリと同じ経路）。窓は 900×420。IME なし（`simulate_input`）。

キャレットを 2 行目の 6 桁に置き、次の 3 つを順に行う。繰り返しの前に 1 回だけ慣らし（その行のキャッシュが入った状態にする）。

1. Right 1 回
2. `x` を 1 文字打つ
3. Backspace 1 回（文字は元に戻る）

1 つの手順を、次の部分に分けて測る。**時間**は、その部分を 1 回流した時間。**常駐の山**は、その間に、常駐メモリの最大（`VmHWM`）が、始める前の常駐（`VmRSS`）より何 MiB 上がったか（Linux だけ。`/proc/self/status` を読む）。部分ごとの確保バイト数は、`unsafe` なしでは取れないので測っていない。代わりに、数え役が、行をデコードしたバイト数とレイアウトしたバイト数を、呼んだ場所ごとに数える（「下の層」の表）。

| 部分 | 流したもの |
|---|---|
| キー | `simulate_keystrokes` / `simulate_input`。キー割り当て → コマンド → `DocumentLayout::edited` → キャレットを見える所へ → GPUI が続けて走らせる再描画（`render`・`prepaint`・`paint`）まで |
| 2 回目の再描画 | キーのあと何も変えずに、もう 1 回再描画（キャレットの点滅など、文書が変わらない再描画と同じ） |
| ステータスバー | `EditorView::status`（行・桁・文字コード・選択）。アプリでは、窓（`Workspace`）がキーのたびに呼ぶ |
| キャレットの x と水平スクロールの範囲 | ルーラーのキャレット印とスクロールバーのつまみの元。`caret_x` と `h_right_edge` |
| ミニマップ | `minimap_rows`（ミニマップを出しているときだけ要る） |
| 対応する括弧 | `bracket_marks::marks`（実際は再描画の中で呼ばれる。ここでは別に流して重さだけ見る） |
| 変更行などの印 | `is_line_modified`・ブックマーク・差分の印を、画面に出る行について |
| タイマー | テストの時計を 10 秒進めて、予定の仕事を流す |

アプリが 1 つのキーのあとにする仕事は、「キー」＋「ステータスバー」（＋ミニマップを出していればミニマップ）。ほかの行は、どの部分が重いかを見るためのもの。「下の層」の表は、`measure` 機能の数え役が見た内側（その関数を呼んだ場所つき）。**入れ子の時間は、中に入っているものを含む**ので、足し合わせてはいけない。

検索の印をつけた場合（パターンは行に無い文字列）も、同じ手順で測った。

### 手元の機械

aarch64、12 スレッド、メモリ 32 GiB、WSL2（Linux 6.18）。Rust 1.99、リリースビルド。ほかのエージェントがこの機械を使っていて、時間には数 % から 2 割のゆれがある（各部分、3 回のうち最も速い回）。Sandbox（Windows ARM64、WARP、8 GB）の測定とは別の機械なので、時間は同じにならない。形を見る。

- `open_file` は、ファイルを全部読んで行末の索引を作るだけ。時間はファイルの大きさに比例し、メモリは 1 倍（200 MiB で +200 MiB）。
- 窓とビュー（`EditorView::new`）が、200 MiB で約 2.3 秒。中身は、**1 行を 2 回レイアウトする**（`lay_out_lines` が 1.03 秒、最初の描画の `line_layout` が 1.00 秒。どちらも `layout_line` で 1 行全体を行に分ける）ことと、色づけが約 0.25 秒。下の「原因 1」と同じ仕事。
- **常駐メモリが 2 倍あまりになるわけ**: 開いた直後の常駐は、ファイルのバイト列（200 MiB）と、**2 行目を全部デコードした文字列（`LineLayout::text`、200 MiB）**。2 行目は最初の画面に入っているので、描画が行のレイアウトを作り、その中の文字列が行のキャッシュ（`DocumentLayout` の `Cache`）に残る（数え役は、行のキャッシュが 200 MiB の文字列を作ったことを数え、測定のテストは `LineLayout::text.len()` = 200 MiB を読む）。常駐は、開いた直後の 218 MiB が、ビューを作ったあとに 431 MiB（+213）になる。メモリの使用中の量（ヒープ）は、`unsafe` なしでは取れないので、窓の分とキャッシュの分は分けられない（4 MiB の行でビューを作ると +57 MiB なので、窓の分は約 57 MiB）。この機械の常駐メモリも、最初の描画のあとで 440 MiB で、Sandbox のプライベートバイト（約 440 MB）と同じ大きさになる。行を折り返した行の表（`rows`）は 0.63 MiB（20481 行 × 32 バイト）で、問題ではない。**この機械では Windows の「プライベートバイト」は見えない**。小さなファイルを Sandbox で開いたときの値（窓と GPU の分）を引けば、この説明を確かめられる。
- キャレットを 2 行目に入れた最初の描画と、最初の編集で、常駐の**最大**が約 +400 MiB と +200 MiB 上がる（Sandbox は「約 200 MB ずつ」で、数字は違うが向きは同じ。Windows のワーキングセットと、ここの `VmHWM` は同じ量ではない）。そのあと常駐は元に戻る（一時のコピー）。

（長さの比は 200/64 = 3.1、64/16 = 4、16/4 = 4）

- **どれも行の長さに比例して伸びる**（二乗や、それ以上ではない）。
- 16 → 64 MiB で 4 倍より大きく跳ねる（5〜7 倍）。デコードやコピー 1 回の時間で見ると、16 MiB で 1.2 ms、64 MiB で 25 ms（20 倍）。32 MiB を超える大きな確保（デコードやコピー）から急に遅くなるように見える。（推測: glibc の大きな確保は毎回新しい領域を OS に頼み、最初に触るときのページフォールトを払う。確かめてはいない。Windows のヒープも、大きなブロックは毎回 OS に頼むので、似た形になると思う。）
- 64 → 200 MiB は約 3 倍で、ほぼ長さの比（3.1）どおり。
- **伸びない部分**: キャレットの x と水平スクロールの範囲（0.00 ms）、ルーラー、変更行などの印、タイマー、アンドゥの記録（`core.model.replace_inner`: 0.04 ms）、ピースツリー自体の挿入と削除（`Document::insert`・`delete`: 0.02 ms。200 MiB の行の中でも）、文字幅の数え上げ（`widest_x`: 0.02 ms。16 KiB 以上の行は、索引の長さから下限を出すだけ）、色の状態の更新（`colors_after_edit`: 0.00 ms）。

そこから、上位の原因は次の 3 つ。

### 原因 1: 編集のたびに、長い行を 2 回、全部レイアウトしなおす（`x` のキーの約 77 %）

- 1 回目: `RowLayout::edited`（`crates/matsu-ui/src/layout_adapter.rs:110`）→ `DocumentLayout::edited` → `lines_changed_inner` → `lay_out_lines`（`crates/matsu-layout/src/document/mod.rs` の 372 行目あたり）が `doc.line(i)`（行全体をデコード）→ `count_rows` → `layout_line`（`crates/matsu-layout/src/wrap.rs`。1 行を 10240 桁ごとの行に分ける）。0.95 秒。
- 2 回目: `lines_changed_inner` が行のキャッシュ（`Cache::forget`）を捨てるので、そのすぐあとのキャレットの位置の問い合わせ（`hit::caret_row_pos`、`crates/matsu-ui/src/hit.rs:115` の `pos_to_row`）→ `line_layout` が、キャッシュに無い行を `doc.line` と `layout_line` でもう 1 回レイアウトし、200 MiB の文字列ごとキャッシュに入れる。0.94 秒。
- なぜ行全体に触るか: 行をどこで折り返すかは、行頭から文字を 1 つずつ足して幅を数えないと決まらない。10240 桁（`MAXLINEKETAS`）より長い行は、通常の文書では必ず折り返す。範囲ごとに読む文書にだけ、長い行を固定の長さ（`LONG_ROW_BYTES` = 4096 バイト）で切る道（`DocumentLayout::long_rows`、`Document::is_long_line`）がある。`is_long_line` は、範囲ごとに読む文書の索引（`long_line_bytes()`）が答えるので、全部を読んだ文書では、いつも「長い行ではない」になる。
- 長さに比例（4 MiB で 18 ms、200 MiB で 948 ms。1 MiB あたり約 4.7 ms）。時間はレイアウトそのもの（デコードは 1 回 80 ms 前後）。

### 原因 2: 1〜64 バイトを読みたいだけなのに、行全体をデコードして、さらにコピーする

通常の文書の `Document::rest_of_line`・`line_len`・`line` は、行全体を `String` にする。使う側が欲しいのは、キャレットの前後の数文字。呼び出し側は、`x` の 1 つのキーのまわりだけで次のとおり（200 MiB の行で、1 回 80〜170 ms）。

| 呼んでいる所 | 何のために | 1 回（ms） |
|---|---|---:|
| `crates/matsu-ui/src/view/element.rs:2218`（`overwrite_caret_width`） | キャレットの幅（キャレットの下の 1 文字）。**再描画のたびに**走る（キーのあと 1 回、点滅のたびにも） | 約 177 |
| `crates/matsu-ui/src/view/status_info.rs:156`（`caret_char_code`） | ステータスバーの文字コード（`rest_of_line(.., 64)`） | 約 174 |
| `crates/matsu-ui/src/view/bracket_marks.rs:90` | 対応する括弧を探す前の長さの確認（`line_len`。長さだけが要るのに、行全体をデコードして数える） | 約 100 |
| `crates/matsu-commands/src/context/mod.rs:605` | 編集が行の終わりで LF につながるかの確認（`line_len`） | 約 100 |
| `crates/matsu-core/src/cursor.rs:499`（`char_right`） | Right の移動先（次の 1 文字） | 約 80 |

- `rest_of_line` は、行全体のデコード（200 MiB）に、残りを `to_owned`（もう 200 MiB）で写す。確保が 2 倍になる。
- 1 回の再描画は、キャレットの幅だけで 0.17 秒。**文字を打たなくても、再描画のたびに 0.2 秒かかる**（2 回目の再描画の行）。
- `line_len` は、元のバイト列が 1 つのピースの間は、デコードしないと長さが出ない（`Storages::decoded_len` が、索引のない元のデータを全部デコードして数える）。ピースが分かれると、元のぶんは何度も数えなおす。
- 範囲ごとに読む文書は、この 5 か所がすべて `line_slice`（その範囲だけ）に分けている。全部を読んだ文書では、同じ分け方をしていない。

### 原因 3: 色づけが行全体を走査する（`x` のキーの約 9 %、ミニマップでは毎回）

- 再描画の `colored_line`（`crates/matsu-ui/src/view/colors.rs`）が、行頭から行末まで `line_runs` と `line_end_state` で走査する。0.22 秒（200 MiB）。同じ行の結果は `line_color_cache` に 1 行ぶん残るが、編集で版が変わると作りなおす。
- ミニマップは同じ `colored_line` を呼ぶが、走査の終わりの位置（`upto`）が本体と違い、キャッシュ（1 行ぶんで 1 つ）の条件に合わないので、測定では毎回走査した（0.22 秒）。ミニマップを出していると、本体の 0.22 秒に足される。（本体とミニマップが 1 つのキャッシュを交互に作りなおすはずだが、測っていない。）

### そのほか

- **メモリ**: 1 つの `x` のキーで、行全体を読む・数える仕事が、レイアウト 2 回（400 MiB）、デコード 3 回（600 MiB。`rest_of_line` はさらに `to_owned` で写す）、長さの数えなおし 1 回（200 MiB）ある。一時のコピーが重なるので、常駐の最大は +400 MiB に達する。残るのは、キャッシュの `LineLayout::text`（行の 1 倍）だけ。
- **検索の印**（パターンが行に無いとき）: 再描画ごとに、さらに行全体のデコード＋検索が 1 回（`matches_of_line`。200 MiB で 0.3 秒）。行が 64 KiB を超える行の印は付けない（`MAX_HIGHLIGHT_LINE_BYTES`）が、その長さの確認の `line_len` が全体をデコードするので、確認だけで 0.1 秒かかる。
- **ピースツリーと索引**: 文字の挿入と削除は 2 つのピースになるだけで、0.02 ms。ここは問題ではない。

## 直し方の選択肢（作っていない。ユーザーが決める）

見積もりは、上の表の入れ子の時間を引いた計算で、測ったものではない。200 MiB の行で `x` を打つキー（キー 2.45 秒＋ステータスバー 0.19 秒 = 2.64 秒）が、何秒になるかの目安。

| 直し方 | 直す原因 | 利用者に見える変化 | 目安 |
|---|---|---|---:|
| **A**: 一定の大きさ（例: 1 MiB）を超える行は、範囲ごとに読む文書と同じ「固定の長さの行」（4096 バイトごと）にレイアウトする。全部を読んだ文書にも、`is_long_line` を答えさせる（全部を読んだ文書の索引は、`long_line_bytes()` が `None` で、長い行の途中の位置を答えない。UTF-8 の文書は、桁とバイトが同じなので答えさせるのは簡単。ほかの文字コードは、範囲ごとの文書の索引と同じものを作る必要がある） | 1 | 長い行が、10240 桁ごとではなく、4096 バイトごとに切れる。折り返しの位置が変わる。長い行では、桁が「バイトの数」で出る（範囲ごとに読む文書と同じ）。行の中の位置に応じて、ステータスバーの桁が近似になる。範囲ごとに読む文書が今していることと同じ動き（実装も、テストも、すでにある） | 約 0.75 秒 |
| **B**: 一定の長さを超える行を持つファイルは、大きさにかかわらず範囲ごとに開く（`nHugeFileSizeMB` とは別の条件） | 1・2・3（まとめて） | 開いてすぐは読み取り専用で、走査が終わると編集できる（巨大ファイルと同じ）。色づけと検索の印が長い行にはつかない。Sandbox の測定では、範囲ごとに開いた 300 MiB の行は、キー 1 つが 13〜80 ms、メモリ約 45 MB。ファイルが 209 MB なので、走査にも時間がかかる | 数十 ms |
| **C**: 行のレイアウトを、編集した行の見える所と、そこまでの行だけにして、残りを空き時間に少しずつ足す（最初のレイアウトの `layout_chunk` と同じやり方） | 1 | 編集の直後は、行の行数（スクロールバーの長さ）が近似で、あとから正しくなる。10240 桁ごとの折り返しは変わらない。ただし、キャレットの手前で桁が 1 つ増えると、そのあとの行の切れ目が全部ずれるので、折り返しの位置の再計算は、結局行全体になる | 空き時間に回るだけ（合計は同じ） |
| **D**: 上の 5 か所を、必要な範囲だけ読む（`line_slice` の道。全部を読んだ文書でも、`raw_for_col` はピースのバイト位置から文字の境界を見つけられる） | 2 | 見える変化なし。速くなるだけ | 約 2.2 秒（D だけでは足りない） |
| **E**: 色づけを、画面に見える所の前後だけ走査する（ミニマップも同じ） | 3 | 長い行の中で、コメントや文字列の始まりが画面より前にあると、色が変わりうる（範囲ごとに読む文書は、すでに 64 KiB（`SKIP_LINE_BYTES`）以上の行に色をつけない） | 約 −0.22 秒 |
| **A + D + E** | 1・2・3 | 上の A、E の変化 | 約 0.08 秒 |

- Sakura は、行を全体として扱って編集のたびに作りなおす（`CLayoutMgr::DoLayout_Range`）ので、同じ形の遅さがあるはず。実機では確かめていない。
- A だけでは、デコード（原因 2）と色づけ（原因 3）が残り、約 0.75 秒になる。D と E だけでは、レイアウト（原因 1、約 1.8 秒）が残る。原因 1 が、いちばん大きい。
- **メモリ**: A か B を入れると、行ごとの文字列のキャッシュ（`LineLayout::text`）は、画面に見える 4096 バイトの行だけを持つようになり、2 行目の分の +200 MiB（と、キャレットを入れたときの一時の +400 MiB）が消える。D だけでは、キャッシュは残る。
- 5 か所のうち、キャレットの幅（`element.rs:2218`）は、長さと関係なく**再描画のたびに**走る。長い行の文書では、ほかの直しより先に D を入れる価値がある（点滅のたびに 0.2 秒、というのは、キーを押していないときも動く）。

## 測れなかったこと

- Windows 上の数字（Sandbox の WARP、GPU への描画）は、この機械では出ない。テストの窓には文字の描画がなく、フォントがないため、描画（`ui.prepaint` の中のシェーピングと GPU への送り）の時間は入っていない。Sandbox との比が、約 2 倍で手順どうし同じなので、足りないぶんは大きくないと見る。
- 常駐メモリは、この機械（Linux）の `VmRSS`・`VmHWM`（`/proc/self/status`）。部分ごと・呼び出しごとの確保バイト数は、`unsafe` なしでは取れないので測っていない（時間と、デコード・レイアウトのバイト数と回数は測った）。Windows の「プライベートバイト」は、窓と GPU の分が別に入る。
- 日本語（2 バイト以上の文字）の長い行は測っていない。デコードが ASCII より重くなるが、形は変わらない。
- 折り返さない設定（`Wrap::None`）と、折り返す設定（桁数を指定）は、どちらも長い行で `layout_line` を通る。ここでは、既定のまま（10240 桁）で測った。
- アンドゥの履歴の大きさ: 1 つの編集の記録は文書のハンドルの写し（`Document::clone`、ポインター 1 つ）なので、200 MiB の行でもほぼ 0 バイト。測定の数え役は、記録の時間（0.04 ms）だけ見ている。

# 巨大ファイルの測定（ADR-0020 の 8.1）

巨大ファイルを範囲ごとに読む仕組み（ADR-0020）の、塊の大きさ（64 KiB と 256 KiB）とキャッシュの大きさを決めるための測定のプログラムと、その使い方。

- 測定のプログラム: `crates/matsu-regex/examples/huge_measure/`（窓を開かずに、エディタと同じコードの経路を通る）
- 手動で起動する CI: `.github/workflows/huge-measure.yml`（push と PR では動かない）
- ここに書いた数字は、手元（Linux、WSL2）の小さな実行のもの。ADR-0020 には書かない。塊の大きさと閾値を ADR で決めるのは、CI で 10GB を測った後のユーザーの判断。

プログラムが `matsu-regex` の example にあるのは、正規表現の検索（`matsu-regex`）と、ファイルの処理（`matsu-core`）の両方が要るため。クレートも依存も増やしていない。製品の動作は変えていない。塊の大きさは、`OpenOptions` の `huge_ranged`（キャッシュの塊）と `huge_scan`（索引の塊）にこのプログラムとテストだけが渡す。`matsu.ini` に鍵は足していない。

## 何を測るか

ファイルの種類は ADR-0020 の 8.1 のとおり。

| 名前 | 内容 | 大きさ |
|---|---|---|
| S | UTF-8、1 行 40 バイト、LF | 指定どおり（10GB が S10） |
| C | UTF-8、CRLF（1 行 41 バイト） | 指定どおり |
| T | 1 行が LF だけ（1 バイト）。行数の最悪の例 | 指定どおり |
| L | 改行のない 1 行 | 1GB まで |
| J | Shift_JIS、全角の日本語 | 指定どおり |
| W | UTF-16 LE（BOM つき）、日本語とサロゲートペア | 指定どおり |
| E | EUC-JP、全角の日本語 | 1GB まで |

どれも、大きな buffer を書いて作る（スパースファイルは使わない。内容が本物でないと、走査・デコード・検索の時間が測れないため）。全体の約 9 割の所に、`MATSU-NEEDLE` という行が 1 つある（「最初の 1 件まで」の検索用）。

ファイルごと、塊の大きさごとに、次を測る。塊の大きさは、キャッシュの塊と走査の索引の塊の両方に同じ値を渡す。キャッシュの合計は `--cache-mb`（既定 64）で一定にする。

| 項目 | 中身 |
|---|---|
| open, first block scanned | `open_file` が返るまで（最初の塊が走査されるのを待つ） |
| first window readable | 上に、最初の 60 行を読む時間を足したもの（ADR の目標は 200ms 以内） |
| scan, with opening / throughput | 開くところからの走査の時間と、ファイルの大きさを割ったスループット |
| resident ... | 常駐メモリ（開く前、開いた後、走査の後、最後）と、最大（ADR の目標は 300MB 以下） |
| index in memory | 走査の索引が持つメモリ |
| jump to the middle / end, cold / warm | 真ん中・末尾の画面（60 行）を読む時間。1 回目が冷、2 回目が温 |
| plain / regex search, needle / common text | 文字列と正規表現の検索。「first hit」は先頭から最初の 1 件まで（needle は約 9 割の所）、「whole file」は最後まで（`find` と `find_all`。エディタの検索と同じ経路） |
| save without changes / after one edit | 変更なしの保存と、先頭に 1 文字入れた後の保存（`TextFile::save`） |
| baseline | ファイルを 1 MiB ずつ素直に読む速さ（ディスクの速さ。走査は 70% 以上が目標） |

検索が `--search-limit-secs` を超えたら止めて、「stopped after N s at X % of the lines」と書く（T は行が 10 億を超えるので、止まるのが普通）。L は 1 行全体をデコードするため、検索は測らない（長い行の検索は別の作業）。

## OS の挙動の確認（8.1 の「確かめる OS の挙動」）

小さなファイル（`--checks-mb`、既定 32）で、`RangedFile` で開いたまま、別のプログラムがしたことを真似る。呼び出しの結果と、そのあとに読んだ結果を、レポートの「OS checks」の表に書く。読むのは、キャッシュに入っていない所と、入っている所の 2 か所。

- rename で置き換える（Windows では、開いたままのファイルの上に rename できるか）
- 削除する
- 半分に切り詰める
- 追記する

読んだ結果は、`ok`、`changed outside (detected)`（`RangedFile` が外からの変更を見つけた）、または OS のエラー。mmap は使わないので、SIGBUS は出ない。

## 手元で動かす

```sh
cargo run --release -p matsu-regex --example huge_measure -- \
    --kinds s,c --size-mb 1024 --blocks 64,256 \
    --dir <測りたいディスクの上のフォルダ> --out <レポートを置くフォルダ>
```

| 引数 | 意味 |
|---|---|
| `--kinds` | `s,c,t,l,j,w,e`（`s10` のように数字を付けてもよい。付けても無視） |
| `--size-mb` | 大きさ（MiB）。10GB は 10240 |
| `--blocks` | 比べる塊の大きさ（KiB）。既定は `64,256` |
| `--cache-mb` | キャッシュの合計（MiB）。既定 64 |
| `--dir` | ファイルを作るフォルダ（既定は一時フォルダ）。作ったファイルは、測ったらすぐ消す |
| `--out` | `report.md` と `report.json` を書くフォルダ |
| `--search-limit-secs` | 1 回の検索の上限。既定 120 |
| `--scan-limit-secs` | 走査の上限。既定 600 |
| `--no-save` / `--no-search` / `--no-baseline` | その測定をしない |
| `--checks-mb N` / `--no-checks` | OS の確認に使うファイルの大きさ / しない |

保存は、元のファイルと同じ大きさの一時ファイルを作るので、`--dir` の空きは大きさの 2 倍以上が要る。

注意すること。

- OS のキャッシュ: Linux は root で動かすと、各回の前にキャッシュを捨てる（`/proc/sys/vm/drop_caches`）。そうでないとき、Windows と macOS では、捨てない。「冷」はエディタのキャッシュについてだけ冷で、ディスクから読むとは限らない。レポートの「OS cache」の行に、捨てたかどうかが書いてある。
- メモリ: 走査・検索・保存は 1 つのプロセスの中で続けて動くので、アロケータが持ったままのメモリが次の回に残る。`resident before opening` を引いて読む。最大の値は、Linux では各回の前に数え直す（`/proc/self/clear_refs`）。Windows は数え直せず、プロセス全体の最大になる（レポートに注がつく）。macOS は最大を返さない。
- 保存の後、文書は書いた新しいファイルを読む形に入れ替わる。そのため、保存の測定は、その回の最後に置いてある。

## CI で動かす

Actions の「huge-measure」を `workflow_dispatch` で動かす。

```sh
gh workflow run huge-measure.yml --ref <branch> -f size_mb=1024
gh run watch
gh run download <run id>
```

| 入力 | 既定 | 意味 |
|---|---|---|
| `kinds` | `s,c,t,l,j,w,e` | どのファイルを測るか |
| `size_mb` | `10240` | 大きさ（MiB）。速く試すなら 1024 |
| `blocks` | `64,256` | 塊の大きさ（KiB） |
| `search_limit_secs` | `30` | 検索の上限 |
| `windows_arm` | `false` | `windows-11-arm` でも動かす（空き容量が分からないので、足りなければジョブが止まる） |

`ubuntu-latest` と `windows-latest` の 2 つで、種類を 5 つのジョブ（`s,l` / `c,e` / `t` / `j` / `w`）に分ける。1 つのジョブが、10GB 級のファイルを 1 つ作って測る形にして、20 分ほどに収めるため。ジョブの上限は 35 分（遅いディスクのため）。Linux は一時ディスク（`/mnt`）に、Windows は `C:` にファイルを作る。空きが足りないときは、測る前にジョブが止まる。Linux は root で動かして、各回の前にキャッシュを捨てる。ジョブごとに、`huge-measure-<番号>-<OS>` の名前で、`report.md` と `report.json` を artifact にする（`report.md` はジョブの要約にも出る）。

## レポートの読み方

`report.md` は、機械の情報（OS、CPU、メモリ、コミット、Rust の版、ファイルシステム、引数）、ファイルの種類ごとの表（列が塊の大きさ）、OS の確認の表、の順。`report.json` は同じ数字（`runs[].metrics` の鍵は「項目 (単位)」）。ユーザー名やコンピューター名は入らない（フォルダは最後の名前だけ）。

見るのは、ADR-0020 の 8.1 の目標との差。

- 最初の窓が 200ms 以内か。ファイルの大きさによらないか
- 走査が、baseline の 70% 以上か（キャッシュに載っていないディスクの速さで）
- 常駐メモリが 300MB 以下か（T でも）
- 冷えた状態のジャンプが、ローカル SSD で 200ms 以内か
- 検索の時間と、止めたときの進み具合
- 塊が 64 KiB と 256 KiB で、どちらが良いか

## 手元の実行（Linux、WSL2、512 MiB）

- 機械: aarch64、12 スレッド、メモリ 32 GiB、WSL2（カーネル 6.18）の上の ext4。リリースビルド。root ではないので、OS のキャッシュは捨てていない（baseline が 9〜16 GB/s なのは、キャッシュから読んだため）。ディスクの実力は、この数字からは分からない。
- 引数: `--kinds s,c,t,l,j,w,e --size-mb 512 --blocks 64,256 --search-limit-secs 30`
- 時間: ファイルの作成は 1 つ 1 秒ほど。全部で約 20 分（T の検索が 30 秒で止まるのを 8 回するのと、保存が 1 つ 4〜11 秒の 4 回、が大半）。

| ファイル | 項目 | 64 KiB | 256 KiB |
|---|---|---:|---:|
| S | 最初の窓 (ms) | 10.3 | 25.3 |
| S | 走査 (MB/s) | 663 | 960 |
| S | 文字列検索 全体 (s) | 5.4 | 5.33 |
| S | 正規表現 全体 (s) | 6.16 | 5.81 |
| S | 保存 (s) | 8.09 | 7.97 |
| C | 最初の窓 (ms) | 5.17 | 22.9 |
| C | 走査 (MB/s) | 903 | 1047 |
| C | 文字列検索 全体 (s) | 5.4 | 5.16 |
| C | 保存 (s) | 7.98 | 7.96 |
| T | 最初の窓 (ms) | 20.6 | 81.2 |
| T | 走査 (MB/s) | 208 | 208 |
| T | 文字列検索 全体 | 30 秒で、行の約 20% で止まった | 同左（約 23%） |
| T | 保存 (s) | 10.4 | 10.9 |
| L | 最初の窓 (ms) | 6.75 | 21.2 |
| L | 走査 (MB/s) | 1009 | 1028 |
| L | 保存 (s) | 8.85 | 8.32 |
| J | 最初の窓 (ms) | 4.8 | 12.7 |
| J | 走査 (MB/s) | 1439 | 1340 |
| J | 文字列検索 全体 (s) | 8.83 | 7.94 |
| J | 保存 (s) | 6.21 | 5.62 |
| W | 最初の窓 (ms) | 3.89 | 12.5 |
| W | 走査 (MB/s) | 1624 | 1556 |
| W | 文字列検索 全体 (s) | 4.43 | 4.27 |
| W | 保存 (s) | 3.87 | 3.89 |
| E | 最初の窓 (ms) | 3.98 | 12.6 |
| E | 走査 (MB/s) | 1452 | 1545 |
| E | 文字列検索 全体 (s) | 8.64 | 9.21 |
| E | 保存 (s) | 5.31 | 5.32 |

表にないもの（正規表現の検索、冷・温のジャンプ、メモリ、「最初の 1 件まで」）は、プログラムが書くレポートにある。

この実行から言えることと、言えないこと。

- 最初の窓は、どの種類でも 100ms より短かった。塊が 256 KiB のほうが、64 KiB より 2〜4 倍遅い（最初の塊の走査を待つので、塊が大きいほど遅い、と考えられる。確かめてはいない）。T がいちばん遅い。
- 走査は、T 以外では、毎秒 0.6〜1.6 GB。塊の大きさの違いは小さい（S は 256 KiB のほうが速く、J は 64 KiB のほうが速い。差が雑音かどうかは、この実行からは分からない）。
- 検索は、毎秒 100 MB ほど（行ごとに読んで探す今のコードの速さ）。T は 5 億行を超えるので、30 秒では終わらない。10GB では、S でも約 100 秒かかる見込み（比例とした推測。測っていない）。
- 保存は、毎秒 50〜130 MB。変更なしの保存と、1 文字入れた後の保存で、時間はほとんど同じだった（どちらも新しいファイルに全部書く）。
- OS の確認（Linux）: rename での置き換え、削除、追記の後も、キャッシュにある所もない所も 4096 バイト読めた（Linux は、開いたファイルの実体が残るため、と考えられる。読んだ内容は確かめていない）。切り詰めた後は、どちらの所も `changed outside` を返した。Windows の結果は、CI で測る。

ここから塊の大きさは決めない。実機のディスクで、10GB で測る（手動の CI）。
